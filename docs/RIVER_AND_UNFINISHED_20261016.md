## 1. 自动河流：三条反馈的根因（全部用你的真实底图实测）

量尺：`scripts/tests/tools/_probe_desite_land.mjs`、`_probe_river_three_ways.mjs`、`_probe_river_width.mjs`
（都读你那份 `绒花计划.sitian` 里的 `desite` 底图，**不跑合成 fixture**）。

### 1.1 你的底图长什么样（先把尺子摆正）

```
desite 底图：省份多边形 415 块（全部 kind=land）
             自带河流   160 条（FMG 导入，width 0.03~0.26 / discharge 36~613）
             高度图     133×75 = 9,975 格，格距 14.4 世界单位
             地图尺寸   约 1920×1080
```

⚠️ 注意这个尺度关系：**一张 1920×1080 的图，高度图只有 133×75 格**（一格≈14.4 世界单位
≈14 屏幕像素）。「一格里到底算陆还是海」这件事，本身就是**格心采样**出来的近似。

### 1.2 🔴 越界入海的根因：我上一轮的「并集」口径

自动河流的段来自**高度场**（`h < 20` 算海），而画出来的海岸线来自**省份多边形**。
两份判据在这份数据上的差异（逐格实测，`_probe_phantom.mjs`，**掩膜走产品自己的 `buildLandMask`**）：

| 判据 | 判为陆地的格数 |
|---|---|
| 高度场 `h >= 20` | **3053** |
| 省份多边形（掩膜） | **2960** |
| 两者**都**判陆 | **2850** |
| 🔴 **幻影格**（高度陆 / 掩膜海） | **203 格 = 全部 9,975 格的 2.04%** |
| 反向（掩膜陆 / 高度海） | 110 格 |

而河网的段是「本格 → receiver」两点的连线，于是：

```
145 / 1710 段 = 8.5% 的段，至少有一个端点踩在幻影格上（涉及 90 个幻影格）
```

这些段在**并集**口径下**两端都被判为陆地** → `clipSegmentToLand` 走进
`if (aLand && bLand) return { ...seg, endInSea: false };` → **一次裁剪都不做**，
河就照着格心画进海里。直接量「两端都判陆 → 跳过裁剪」的段数：

| 口径 | 两端都判陆（= 跳过裁剪）的段数 |
|---|---|
| **并集（上一轮的现状）** | **1034** |
| **掩膜独占（本轮修法）** | **854** |

→ **180 段**在并集下"不用裁"，其中相当一部分正是画进海里的那些。

> 🔴 **量尺自己也踩了坑（留档）**：我第一版量尺（`_probe_desite_land.mjs`）**自己手写了一个射线法**
> 来判"点在不在省份内"，读出 **101 格**；换成产品真正用的 `buildLandMask` 读完是 **203 格** ——
> **少了一半**。差异来自我那份手写实现的环/洞/重叠处理与产品不一致。
> **纪律：量任何"产品口径"的东西，一律 import 产品的实现，不要另写一份。** 那份量尺已删。
> 本项目在"诊断工具自己踩坑"上已吃过两次（`dump_river_clip.mjs` 把点读成 NaN）。

> 我上一轮写的「改成 掩膜 ∪ 高度 之后 → 9/2785」，
> 量的是「**裁剪之后**仍越界的段」，而并集让**大量段根本没进裁剪**。
> 两者不矛盾，是**量错了对象**。这是我第三次在同一件事上给自己发假证据。

**修法**（`ScenarioMap.makeRiverLandCheck`）：
- 掩膜在 → **掩膜独占**：`if (useMask) return (x, y) => !!mask.lookup(x, y);`
- 掩膜不在（还没画省份的空底图）→ 才回退高度场 `return heightIsLand;`
- 好处：与「源头必须离海 ≥2 格」那道闸门**终于同口径**（那道闸门本来就是纯掩膜），
  不会再有「源头在海上、河道在陆上」这种自相矛盾。

🔴 **可复用的判据**：当两份判据对同一件事给出不同答案时，取**真正决定画面的那一份**。
这里画出来的陆地是省份多边形（海岸线由它重建），高度场只是格心采样的近似 → 掩膜赢。

### 1.3 🔴 色差的根因：我对齐的是「数据里的默认色」，不是「画出来的那个色」

上一轮我把自动河的颜色对齐到 `utils/rivers.js` 的 `RIVER_COLOR = '#3B82F6'`。
**那个色从来没被画出来过** —— 它是手画河**写进数据**的默认值。地图上真正的自带河是另一套：

| | 自带河（FMG 导入，`drawRivers`） | 自动河（上一轮） |
|---|---|---|
| 颜色 | `#5d97bb` | 外层 `#3B82F6` @alpha 0.35 + 内层亮芯 `#93c5fd` |
| 描边遍数 | **单遍实线** | **两遍**（光晕 + 亮芯） |
| 线宽量纲 | **屏幕像素**（不随缩放变） | 世界单位（随缩放变粗） |
| 实测线宽 | p50 **0.70px** / max 2.55px | p50 **0.80px 实心 + 1.92px 光晕** |

自带河 160 条的线宽分布（`_probe_river_width.mjs` 实测）：
`min 0.70 / p25 0.70 / p50 0.70 / p75 0.70 / p90 0.74 / max 2.55` → **141/160 = 88% 被夹在 0.7px 下界**。
也就是说「自带河」在这份数据上本来就基本一样粗。

于是：自动河 = **发光的、两遍的、会随缩放变粗的中蓝带子**；
自带河 = **贴地形的、单遍的、不随缩放的细暗线**。
同屏一眼就是两套东西 —— 用户说的「色差 / 各画各的」是**准的**。

**修法**：
1. `utils/riverRender.js` 新增 **`BASEMAP_RIVER_COLOR = '#5d97bb'`**、
   **`basemapRiverWidthPx()`**（**逐字**复制 `drawRivers` 那条公式）、
   **`flowToDischargeEquivalent()`**（把自动河的 `flow` 按**本幅图段流量上界**归一化后
   映射到实测 discharge 区间 36~613）。
2. `strokeRiverNetwork` 新增 **`widthPx`（屏幕像素直给）** + **`solid`/`singlePass`（单遍实线）**。
3. `ScenarioMap` 的自动河改成：`strokeStyle: BASEMAP_RIVER_COLOR` + `solid: true` + `widthPx`。
4. 顺手统一了**第四处**写死的 `#5d97bb`（河流编辑器预览 `riverDraft`）——
   前三次分别在 `drawRivers` / `drawRiverPaths` / 自动河，这次全走常量。

⚠️ 一个诚实的取舍：**宽河在缩小时会被下采样变得不明显**。
自带河因为细，缩小时反而更"稳"。如果你觉得自动河缩小后看不清，
那是「细线 vs 粗线」的取舍，可以再调 `RIVER_W_MIN/MAX` 或加一档"随缩放的淡出"。

### 1.4 「各画各的」—— 量完之后，答案是"把选择权交给你"

上一轮我只统一了**画法**（色/线宽/单遍），**没有量几何**。这一轮补上了两支量尺。

**① 两套河不是同一条河**（`_probe_river_align.mjs`，世界单位 ≈ 屏幕像素 @zoom=1）：

```
自动河网段 → 最近的自带河：  中位 18.78（≈1.3 格）  p25 7.94  p75 37.64
  ≤1 单位 7.1%   ≤3 单位 9.9%   ≤5 单位 16.1%   ≤20 单位 52.4%
自带河顶点 → 最近的自动河段：  p50 5.66
  ≤3 单位 39.9%    ≤5 单位 47.7%
```

→ **只有 10% 的自动段落在自带河 3 单位内**。它们走的是**不同的谷**，不是"同一条河画了两遍"。

**② 但"不一样"不等于"我错"**（`_probe_river_valley.mjs`，两套河同一把尺）：

| | 谷底度均值（邻域均值−本格） | 在谷里比例 | 相邻点"往上流"比例 |
|---|---|---|---|
| 自带河（FMG） | **1.80** | 62.0% | **49.9%** |
| 自动河（段） | 0.48 | 53.3% | **7.8%** |

⚠️ **这个读数有一个我必须说清的坑**：FMG 的河点**不在格心上**（是插值出来的平滑几何），
把它按最近的格心去比高度，本身就带 ±半格（≈7 世界单位）的量化噪声 →
那 49.9% 的"上升"**主要是我的量法造成的**，不是 FMG 让水往上流。
而自动河的段是**格到格**的，网格步进天然是单调的 → 7.8% 是结构性的。
**结论：这条尺子排不出谁更好，我不拿它当判据。** 它只说明两套河各自都与这份地形相容。

**③ 所以真正诚实的做法是——不替你选**。我**没有**把默认改成"只画自动"（那会让「自动河流」
一按就**把你原来的 160 条河藏掉**，是破坏性默认；本项目在"隐式载入覆盖项目数据"上吃过这种亏）。

**做法**：在「自动河流」按钮旁加一个 **`data-testid="river-source"` 下拉**，三档：

| 档位 | 行为 |
|---|---|
| **河流：两套都画**（默认） | 与以前**一字不差** |
| 只画底图自带 | 藏掉自动河（保留 FMG 那 160 条） |
| 只画自动生成 | 藏掉自带河 —— **这就是你要的"一套河"** |

并且点完「自动河流」后，状态栏回执里会**直接告诉你这条路**：
「💡 底图自带河流会与它并存（实测是**两套不同的水系**）—— 想只留一套请把旁边的「河流」下拉选成「只画自动生成」」。

🔴 另一条只**量出来、没改**的路（留给你定）：让自动河**只补自带河没有的地方**
（按自带河走向做排斥带）。那能同时保住两套信息且不重叠，但会改变自动河的覆盖范围，
属于产品决策，我不擅自动。

## 2. 你问的三个问题

### 2.1 历史剧本到底是什么逻辑？

**答案：以「底图」为单位选时间；一个剧本 = 该底图上某一段时期的版图快照 + 易主日期表。**

数据模型（你的项目文件实测）：

```
scenarios.baseMaps.desite        ← 底图：415 省几何 + 160 河 + 高度图（几何在这里）
scenarios.scenarios['desite/瓯王朝']  ← 剧本：ownerKey='desite' + era{startYear,endYear}
                                        + polities + ownership{415 省} + changeEvents
```

- **剧本不持有几何**，它只有「哪个省归哪个势力」+「哪年易主」。12 条剧本**共用** desite 的 415 省。
- **剧本键 = `底图键/剧本名`**，并且 `ownerKey` 字段指向底图 → 所以**你期望的"每个剧本对应一个时间节点"是对的**，
  但**"选剧本会不会自动换底图"的答案是：不会**。
  - `selectScenarioAt` 只做三件事：切当前剧本 + 跳到该时期起始年 + 同步游标。
  - 反方向才有联动：**换底图会顺手选中该底图的第一条剧本**。
  - 时间轴只装**当前底图**的剧本 → 两张底图的剧本**不可能同轴播放/比较**。
- **底图确实被"锁住"了**：`ownerKey` 只在**创建/继承**剧本时写入，
  `updateScenario` **不含 ownerKey** → 你那 12 条剧本**永久绑在 desite 上，UI 上无法改挂**。
- **一个剧本内部不是"一个时刻"**：`ownership` 的语义是**本剧本结束时**的状态，
  区间内的易主由 `changeEvents[省] = [{y,m,d,owner}…]` 承载 → 游标停在年内不同位置，着色会不同。
  且默认易主日期是**合成值**（区间内均匀铺开、只到年），UI 自己也写着「不是史料」。
- 年份的唯一来源是 `era.startYear/endYear`；排序用的是 `order`（不是年份）。
- ⚠️ **切片点的 UI 只能新增**：`renameSlicePoint / updateSlicePoint / removeSlicePoint`
  在 `src/` 里**零 UI 调用**（只有用例直接调 store）→ 你建了书签之后**不能改名/改日期/删除**；
  且书签在轨道上**没有自己的点击 handler**，点它只会落到轨道按 x 取整到**年**。

**三个入口，三种语义**（这块是 2026-10-06 那次数据毁伤之后刻意分开的）：

| 入口 | 读哪儿 | 语义 |
|---|---|---|
| 世界选择页「历史剧本」 | 知识库缓存 `<库>/.sitian/scenarios.json` | `fillMissingOnly`（**内存优先、只补缺**，且**不碰切片点**） |
| 打开项目 | **项目文件的 `scenarios` 键** | `fresh: true`（整体替换） |
| 「导入剧本数据（合并：同 key 覆盖）」 | 你选的文件 | 默认合并（新值赢） |

### 2.2 「分辨率」按钮到底是什么、怎么测？

**一句话**：把当前底图的**高度图**做**双线性放大**（连续量 h/temp/prec 插值，分类量 biome/culture 等走最近邻），
**2~8 倍、单次上限 400,000 格、一条 undo、可 Ctrl+Z**。
它**只让地形表达更细，不增加信息**，也**不动省份几何与导入河流**。

对 `desite`（133×75 / 9,975 格）的读数：

| 倍数 | 新格数 | 内存 | 预计耗时 | 档位 | 能应用吗 |
|---|---|---|---|---|---|
| ×2 | 39,485（265×149） | 约 2.6 MB | 39 ms | fast | ✅ |
| ×3 | 88,531 | 约 5.8 MB | 89 ms | ok | ✅ |
| ×4 | 157,113（529×297） | 约 10.3 MB | 157 ms | ok | ✅ |
| ×6 | 352,885 | 约 23.2 MB | 353 ms | slow | ✅ |
| ×8 | 626,801 | — | — | reject | ❌ 超 40 万格 |

**手工测试步骤**（约 1 分钟）：
1. 世界选择页 →「历史剧本」→ 底图下拉选 `desite`；
2. 工具栏「更多」展开 → 点带文字的「**分辨率**」；
3. 先记下面板右上那句**成本预估**（默认 ×2）；
4. 「**底图图层**」下拉切到「**地形高度**」（默认是「陆海底色」）→ 滚轮放大到 200%~400%，
   **先记住海岸线/山坡的方块台阶有多大**；
5. 把「放大」改成 ×4 → 看预估数字**跟着变**；
6. 点「**应用分辨率**」→ 面板收起，状态栏报新格数/格距 → **再放大看，台阶变小了**；
7. `Ctrl+Z` → 台阶尺度回到原样（一条撤销就是回退）。

**注意事项**：
- 点「应用分辨率」**没有二次确认**，立刻改数据；唯一兜底是 `Ctrl+Z`（栈上限 100 条）；
- 未绑定行星时写 `baseMaps[key].heightmap`；**若底图绑定了行星，改的是行星那份**，共用它的剧本会一起变；
- **平滑地形不重算派生量**（只改 h），想要温度/降水/群系跟着走要另点「重算派生图层」；
- ⚠️ **已知缺陷（本轮新发现，未修）**：×8 被拒后，红字里建议的「7 倍」**本身仍然超限**
  （133×75 的 ×7 = 480,075 > 400,000）。拒绝分支只做 `f-1` 就不再复核。
- ⚠️ **疑似缺陷（静态读代码得出，未真机验证，未修）**：`resampleHeightmap` 只把
  「长度 == 格数」的键搬进新对象，而 FMG 解析器把 `biomes/cultures/religions/states`
  四张**元数据表**也挂在 `heightmap` 上 → **重采样后这四张表可能消失**（表现为文化/宗教下拉与图例变空）。
  「平滑地形」不受影响（它 `{...hm, h}` 保留其余键）；`Ctrl+Z` 会换回原对象，不是永久丢，但 `Ctrl+Y` 会再丢一次。

用户定调：「保底也要做，强化地图编辑器本身，让用户可以随心所欲画河流，能画好看」，

**本轮做了三件（跨两图同一条契约）**：

1. **下沉出 `utils/polylineSmooth.js`（平滑的单一实现）**：`smoothPolyline`（Chaikin 角切割）
   + `decimatePolyline`（笔迹抽稀）+ `smoothRiverNodes`（**带高度**的平滑）。
   🔴 为什么不放在 `riverTrace` 里：`provinceShape`（省份渲染**热路径**）也要平滑，

   "从高到低"的流向不变量就维持不了。所以每个平滑点取**最近原点**的 h，

   回执写明「笔迹 N 点 → 抽稀 M → 平滑 K 点」。

3. **行星图**：新增**拖笔收点**（`riverBrushStart/Move/End`，包在既有 interactions 回调外面）。
   🔴 **顺序是关键**（读 `useCanvasRenderer` 确认）：`onDragStart → onDragMove* → onDragEnd →（有位移则抑制）onClick`；

   判据用**抬笔时的笔迹点数**（<4 视为"只是点击"）而不是"有没有 drag"—— 拖 2px 手抖不该被当成画河。
   分工：**拖出笔迹 → 成河**；**只是点一下 → 原来的放描点/选中/加拐点**，两条路都保留。
