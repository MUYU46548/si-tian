### 1.10 资料线小结

- 最要命的**不是**“字段不够多”，而是 **B0（缺索引直接失败）**、**B1（只认两个目录）**、**B8（缓存过期不刷新）**：这三条决定了“换一个库就什么都读不到 / 库里有但司天里没有”。
- 应用内阅读器**已经存在**（`NodeDetailPanel`），缺的是「任意笔记的入口 + 应用内双链 + 附件协议」；这比从零写阅读器便宜得多。
- **B9（概念混同）**：`audit-coverage` 把 270 篇人物/组织/事件判为“本就不该成为地图节点”——这个判断对；但产品没有给它们第二个身份（资料条目）。资料线要做的不是把这 270 篇塞进地图，而是让它们**可读、可搜、可绑定**。
- 结论与规划一致：**在提取器旁边加一层只读全库索引**，不要重写提取器；但 B0 必须先修（它会让新索引也拿不到启动数据）。

### 2.0 先算一遍：`/3` 切线让每段边界鼓出 6%~30%

**探针**：`node scripts/tests/tools/_probe_bezier_overshoot.js`（纯函数，不依赖应用）

| 环 | 最大鼓出（世界单位） | 最大鼓出 / 弦长 |
|---|---:|---:|
| 正方形（边长 100） | **25.0** | **25.0%** |
| 正六边形（半径 100） | 21.65 | 21.65% |
| 正二十四边形（半径 100） | 1.69 | 6.47% |
| 不均匀环（24 点，±35% 抖动） | 9.38 | **30.0%**（平均 12.75%） |
| 稀疏环（8 点，±45%） | 19.25 | 21.07% |

**代码证据**：
- `ScenarioMap.vue:7063-7075`：`withBezierControls` 用 `out = (next - prev) / 3`；标准 Catmull-Rom → 三次贝塞尔是 `/6`，**切线长了两倍**。
- `ScenarioMap.vue:7090-7093`：`traceShapePath` 用 `prev.controlOut` + `cur.controlIn` 画 `bezierCurveTo`。
- `ScenarioMap.vue:4906`：自由绘制落库时就把这套控制点**写进数据**；`:3681` 在第一次点顶点时也会补写。
- `utils/polygonBool.js` / `provinceShape`：布尔与命中只用**顶点**，不认控制点。

**含义**：
1. 数据多边形的边是弦，渲染曲线在弦外鼓出去；**看到的边界 ≠ 算到的边界**。点选/布尔/面积都按弦算，所以“看着在里面、点不中”是必然的。
2. **只有带控制点的省才这样**。导入的 `desite.map` 省没有控制点 → 渲染走 `lineTo`，反而正常；一旦自由绘制、或点过一次顶点，就开始鼓。这正好解释“导入底图看着还行，新画的省很怪”。
3. 鼓出比例跟**点数/均匀度**强相关：RDP 后点越稀、越不均匀，鼓得越厉害（±35% 抖动时最大 30%）。
4. `/6` 只是把鼓出减半（正方形仍有 12.5%），**不是根治**；根治要么不用控制点（布尔结果就按弦画），要么把平滑后的点写回数据、让渲染与布尔同源。

**✅ H1a 已修（2026-10-19）**：自由绘制/描点落库**不再写控制点**，预览也不再套贝塞尔 → 数据=渲染；
`withBezierControls` 只留给“用户点顶点显式加手柄”，并改成 `/6` + 相邻段长夹紧。判据 `test_113`（控制点 0）+ `test_20`。

### 2.2 🔴 描轮廓：一笔横扫 12 省，清空 3 个

矩阵里 02 号那一笔（45px 半径、贴着 `province_1`/`province_2` 的边界画一圈）状态栏原文：

> 描轮廓：从「Nipal-Zedlyn」挖去一块、从「Goragh」挖去（**已清空**）、并入「Lothiylnar」、从「Enegrefrant」挖去一块、从「Hlaugref」挖去一块、从「Commachamenz」挖去一块、从「Ghronzan」挖去（**已清空**）、从「Lolth」挖去一块、从「Haulssad」挖去一块、从「Ormoklynghrog」挖去一块、从「Ugheindylran」挖去一块、从「Chaul-Did」挖去（**已清空**）、从「Arithlondreth」挖去一块（笔迹 31 点 → 简化 15 点；围住 18513、实际搬动 13328：「Ghronzan」→「Lothiylnar」，贴着「Lothiylnar」描）—— 邻省已自动重算，一笔 = 1 条撤销

**为什么**：`resolveOutlineRegion`（`provinceEditing.js:482-560`）把笔迹围住的区域与**所有**相交省做一次 `difference`，目标省做 `union`；目标省按“笔迹点落在谁里面最多”自动选。边界密集处一笔会同时压到十几个省，于是“一条线改一圈邻居”成立——语义上是设计，体感上是**一笔毁图**。

**可感**：用户只想把一段边界推过去，结果三个省消失、九个省缺角；虽然 Ctrl+Z 能回来（矩阵实测 undo=1），但**落笔前没有任何“这一笔会影响谁”的预告**。

**修法方向（T9）**：
- 落笔预览就把“将被挖/被并的省”高亮出来，并在状态栏给“影响 N 省 / 总面积 X”；
- 面积或省数超过阈值（例如 >6 省，或搬动 > 全图 5%）先问一句，或拒绝；
- 默认 `toNeighbor` 改为 **false**（只修形状，不换主），换主必须显式选目标省——这与 `v2.0` 的“线跟着笔走、邻居自己更新”不冲突，只是把“换主”从默认改成显式。

**✅ H1a 已修（2026-10-19）**：影响省数 >6 → `province-gate` 拒绝（零副作用），确认后 `allowMany` 重试；
默认 `outlineToNeighbor=false`；回执带“影响 N 省”。判据 `test_126`（9 省被拒/8 空省/undo）。
**仍未做**：落笔**前**的地图高亮预览（现在是松手后闸门 + 确认）。

### 2.3 画布会被面板压到 541×200

同一次矩阵里，画布矩形随工具/面板变化：

| 状态 | 画布 |
|---|---|
| 刚进剧本（选择工具） | **1080×484** |
| 切到省份笔刷（省份行出现） | 1080×404 |
| 切到描轮廓 | 1080×415 |
| 切到底图类（高度/河/文化…） | 1080×390~430 |
| 多次工具后（属性面板 + 时间轴都开着，实测一次） | **541×200** |

`541×200` 那次是连续切工具后出现的（属性面板保持打开 + 底图编辑行展开）。在这个尺寸下，一个省只占几十像素，**画省/描边基本不可用**。这不是“画不出来”的唯一原因，但它是“打开工具就想关掉”的直接来源。

**修法方向（T10）**：工具栏分组后，工具参数用**浮层/单行**而不是常驻面板；进入绘制时自动收起属性面板；画布最小尺寸给一个下限（例如 <700×400 时提示“收起面板再画”）。

**🟡 H1a 已做一半（2026-10-19）**：<700×400 时状态栏提示一次（`handleResize` 的 `smallCanvasWarned`）；
**未做**：参数浮层化 / 自动收面板 / 布局最小尺寸约束。

### 2.4 被挖空的省留在数组里（n=0）

`applyRegionToTerrain`（`provinceEditing.js:398-429`）在 `difference` 把省挖空时只记 `emptied: true`，返回的省仍有 `points: []`；矩阵里 `Goragh` / `Ghronzan` / `Wrogbig` 都是 `n=0` 但**仍在 terrain 数组**（总数仍 200）。

**可感**：省列表/编号/势力归属里会多出“看不见的省”；后续按索引选目标省时可能选中空壳（`provBrushTarget` 是 1-based 下标）。这不一定是本轮用户看到的主症状，但它是“越画越乱”的隐形来源。

**修法方向（T9 顺带）**：挖空后从 terrain 移除（并级联清理剧本 ownership / 标签），或至少标 `empty: true` 并在目标省下拉里过滤；两种都要有判据。

**✅ H1a 已修（软路线，2026-10-19）**：挖空即标 `empty: true`；`ScenarioMap` 的目标省下拉过滤 `empty`
（带原始下标，避免错位）；undo 后空标记归零。判据 `test_126`（8 空省 / 下拉只剩 4 / undo 还原）。
**仍未做**：物理删除空省 + ownership/标签级联。

### 2.5 能用的部分（不要重做）

- 画/涂/圈/河的**数据写入链**是通的：一笔一条撤销、状态栏有可读回执、布尔层有兜底。
- 高度/群系/文化/宗教四个笔刷都能写通道（undoLabel 与像素差都对）。
- 河流橡皮的“段删除 → 断成两条”语义成立。
- 这些结论与上一轮“拖动中 18.5ms”的性能数不冲突：慢的是保存，不是笔迹。

## 5. S0 结论（先做什么）

1. **B0 必须排在资料线第一件**：索引缺失时提取不能整次失败；这是“换库即空”的直接原因。
2. **B1/B2 是 T1/T2 的本体**：范围可配 + 字段可映射 + 候选确认。
3. **B6/B7 是 T3 的本体**：阅读器已有，补“任意笔记入口 + 应用内双链 + 附件”。
4. **手绘线先修“安全”再修“手感”**：描轮廓的破坏面（§2.2）是数据风险，排在 `/3` 鼓出之前；空省残留（§2.4）与它同一件修；画布被面板压小（§2.3）在 T10 一起做；最后才是笔迹引擎。
5. 手绘线“全部名存实亡”的判断**不成立**：12 个工具里 11 个确实改了数据（§2.1）。下一轮不要从“重写”开始，从**形状 / 安全 / 画布**三处修。
