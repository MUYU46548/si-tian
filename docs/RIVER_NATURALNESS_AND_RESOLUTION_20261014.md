## 四、2026-10-15：实测截图回来的四条修正

暮雨拿两张画布截图报了四条。**三条里我上一轮的判断不够或错了**，逐条记下来。

### 4.1 「河流并没有越往下游越宽」——我的线宽口径选错了（真错）

**实测根因**（`scripts/tests/tools/dump_river_flows.mjs`，真实 desite）：

```
逐点汇流量：min=2 p10=2 p50=5 p90=8 max=9
条 len=5  flows : 2 3 6 8 9
         widthW: 1.49 1.63 1.91 2.05 2.11      ← 整条河 1.41×
```

我上一轮用的是**绝对**口径 `0.55 + cbrt(flow) * 0.75`。它假设 flow 能到几百上千
（那时 1 → 1.2、512 → 4.9 确实拉得开），而**这份地形的 flow 只有 1~20** ——
立方根把窄量程压平了，整条河从 1.49 涨到 2.11，**1.4 倍**，肉眼就是一样粗。

**修法**：改成**相对**口径 `flowWidthScale(flow, maxFlow)` —— 按本幅图的流量上界归一化
（`t = (f-1)/(max-1)`，再 `min + (max-min)·√t`）。形状用 `√` 而不是立方根：归一化之后
0..1 区间上 sqrt 给低流量更多区分度（0.05 → 0.22），cbrt 会把细支流全压到 0.37 以上。

实测（用例地形，段汇流量 1~1275）：**0.8 → 5.0 世界单位（6.25×）**。
真实底图（段 1~20）在同一口径下是 **0.8 → 3.3（4.1×）**。
Node 单测钉死：窄量程（1~20）上粗细比 **>3 倍**，且**必须显著优于旧绝对口径**（>2 倍）。

### 4.2 「根本画不出复杂的河流汇聚（树枝状）」——我的几何口径选错了（真错）

**实测根因**（`scripts/tests/tools/dump_river_network.mjs`，真实 desite）：

| 源头高度 | 代表路径条数 | 总点数 | **覆盖格数** | 陆地格 |
|---|---|---|---|---|
| >60 | 3 | 12 | **12** | 2506 |
| >50 | 16 | 66 | 61 | 2506 |
| >40 | 67 | 270 | 188 | 2506 |

上一轮我把 `rivers[]` 当成河网的**全部**，而它其实是"每个源头一条**代表路径**"——
一条折线从头走到海，**不包含**沿途汇进来的支流。所以画面上必然是几根孤立的线，
**结构上不可能**出现树枝状汇聚。这条是我判断错了：我以为"合并去重"能让它更像河网，
实际上它连"网"都不是。

**修法**：输出**河网的几何本体 —— 段**（`traceRivers().segments`）：每个能到海的陆地格
一条 `本格 → 它的接收格` 的段，段宽取该格的汇流量。实测 desite **1717 段**
（占 2506 陆地的 68%），支流逐格汇进干流。渲染走新函数 `strokeRiverNetwork`
（`utils/riverRender.js`），两遍描边与单条河同一套口径。

⚠️ **`rivers[]` 不删**：它仍是"命名/分级"的对象（未来要挂桥/水坝/名称、做时间轴）。
段负责**观感**，路径负责**身份** —— 两者是同一次追踪的两个视图。

⚠️ **如实交代**：段是"每格一小截"，理论上会有**绘制重叠**（相邻段共享端点）。
圆头 + 同一颜色下看不出来，但段数多时每帧调用数上升：
用例地形 3750 段 → 每帧 3750×2 = 7500 次 `stroke`，实测（`test_103`）**点一次 165 ms 里
大头是追踪与裁剪，渲染本身在这个量级没有可感延迟**。真实底图 1717 段更少。

### 4.3 「依然过度延伸到海洋部分」——自动河这一侧确实没裁（真漏）

上一轮我给**导入河**（FMG 的 `.map` 几何）加了海岸线裁剪，但**自动河流**这一侧漏了：
段的一端是**海格中心**，而画出来的海岸线在格与格之间 → 每一条入海段都越过岸线插进海里。

**修法**：新增 `utils/coastline.js` 的 **`clipSegmentToLand`**（段版本）——
与导入河/手画河**共用同一个 `crossingPoint` 二分**（两处各写一套就会出现
"进口河不出界、自动河出界"这种最难查的不一致）。画布侧 `getAutoRiverNetwork()`
按 `terrain` 引用 + `autoRivers` 引用缓存裁剪结果（不缓存 = 每帧两万次射线判定）。

🔴 **裁到一半发现的第二层问题 —— "两份陆地判据对不齐"（实测，差点被它带偏）**：
河网的段来自**高度场**（`h < 20` 算海），而海岸线掩膜来自**省份多边形**。两份判据在海边
必然对不齐（高度是格心采样、海岸线从格子里穿过）。实测 desite（`dump_river_clip.mjs`）：

| 判据 | 裁之前陆端在"陆地之外" | 裁之后 |
|---|---|---|
| **只按省份掩膜** | 693 / 2610 | **776 / 2785**（反而更多！） |
| **掩膜 ∪ 高度**（实际采用） | — | **9 / 2785** |

只按掩膜判时，那些"高度上算陆、多边形上算海"的格会被**反复裁/丢**（整段丢 238 条），
看起来就是"河到这里就断了"。所以自动河流的裁剪前提是**并集口径**
（`makeRiverLandCheck`：掩膜 ∪ 高度场，高度按规则栅格 O(1) 定位）。
剩下 9 个是真正骑在边界上的格（`h=10`/`h=19` 那种，两边都判水）—— 属数据 fuzz，不装作已解决。

⚠️ **与"源头必须离海 ≥2 格"那道闸门不冲突**：那道闸门用**纯掩膜**口径（管**源头**，宁严），
这里管**画出来的几何**（宁全）。两者口径不同是**有意的**，不是不一致。

⚠️ **诊断工具自身踩的一个坑（留档）**：`dump_river_clip.mjs` 第一版写 `points[0][0]`，
而抽出来的网格点是 `{x,y}` 对象 → 全 `NaN` → `heightIsLand` 恒 false →
"并集口径"**静默退化**成纯掩膜，读数与掩膜一模一样（差点把结论带偏）。
**两种形态都要认**（组件里 `makeRiverLandCheck` 本来就写了兼容）。

Node 单测 4 条：陆→水裁到岸线、水→陆方向反过来也对、全陆原样（`endInSea` 清零）/全水丢弃、
判定抛错不误删（保守当陆地）。

### 4.4 「有色差（与地图自带河流相差明显）」——同一画面有三种蓝（真缺陷）

实测（读源码）：

| 出处 | 颜色 |
|---|---|
| `utils/rivers.js` 的 `RIVER_COLOR`（手画河**写进数据**的默认色） | `#3B82F6` |
| `ScenarioMap.drawRiverPaths` 实际描边（**写死**） | `#5d97bb` |
| 自动河流上一轮自选 | `#4f93b8` |
| FMG 导入河 | 按数据里的 `color` |

也就是**手画河"数据是 #3B82F6、画出来是 #5d97bb"**，再加自动河流第三种 —— 三色并存。

**修法**：`RIVER_STROKE` 改为**从 `rivers.js` 导入 `RIVER_COLOR`**（单一来源），
`drawRiverPaths` 的写死色也换成同一个常量。亮芯色相应调成 `#93c5fd`（低 alpha 高光，
不再自成一种蓝）。⚠️ FMG 导入河仍按数据里的 `color` —— 那是**数据**不是画法，
统一它属于改用户数据，不在本轮范围。

### 4.6 「内流河」的评估：**这份地形画不出内流河，原因不是没实现**

暮雨提到「地图自带河流做的比自动河流好，**还有内流河**」。我把盆地口径量出来了
（`traceRivers().basins` / `endorheicCells`，`dump_river_network.mjs`）：

```
内流：1338 格陆地水出不去（占陆地 44%）；盆地 1338 个 / 面积和 1338 格；
      ≥5 格的 0 个（都是 1~4 格的微洼地）
```

**读法**：内流格**很多**（44%），但**盆地全是"一格一个"** —— 1338 个盆地 = 1338 格，
即**没有任何一个盆地大于 1 格**。所以"画内流河"在这份数据上只会得到 1338 个
**孤立的单格点状物**，那不是内流河，是噪点。

**结论（据实说）**：内流河要**先有盆地**。这份地形（14.4 格距、格内高差 1~2）长不出盆地，
所以真正该做的不是"打开一个开关"，而是二选一：
1. **换更高分辨率/更高起伏的源高度图**（与 2.5「长河」是同一个前置条件）；
2. **让用户手挖洼地**（地形笔刷把一片压低）→ 那时盆地口径才第一次有东西可画。

本轮**只做了度量与出口**（`isLand` 注入时 O(n) 算盆地并回报），**没有**改绘制行为 ——
内流格照旧不画（口径 ②，防"内陆凭空一条河"）。要画的时候，开关与画法都还没有。

## A2、河流「不自然」的真实瓶颈：**这份地形长不出长河**

### 2.1 事实（`desite` 底图，9975 格 / spacing 14.4）

| 指标 | 值 |
|---|---|
| 网格 | 133 × 75 = **9975** 格，spacing **14.4** 世界单位 |
| 陆地（省份掩膜 20 个环判定） | **2506** 格（占 25%） |
| 陆格**离海**距离 | 中位 **3 格**、90 分位 6、最大 **11 格**（= **158** 世界单位） |
| 离海距离直方图 | ≤1 格 699 / ≤2 格 489 / ≤3 格 405 / ≤5 格 532 / ≤10 格 370 / >10 格 **11** |
| 这张图的跨度 | 约 **1913** 世界单位（133 × 14.4） |

**把一个格子约 14.4 单位、离海最多 11 格、图上四分之三是水**这三件事摆在一起，结论只有一个：
**它是一片细碎群岛 + 窄半岛**。水**走不了多远** —— 这不是算法能补的，也不是渲染能补的。

### 2.2 那"改自然"到底改了什么（改了的）

1. **逐点线宽**（`utils/riverRender.js` 的 `riverWidthAt`）
   旧口径：一条河从源头到河口**一个粗细**（只有一个标量 `flow`）。真实河网是**越往下游越宽**。
   现在每条河带 `flows[]`（逐点汇流量），宽度走**立方根**（平方根压不出差别，见下）：
   `flow 1 → 1.30、8 → 2.05、64 → 3.55、1024 → 5.00`（世界单位，下限 0.7 / 上限 5.0）。
2. **两遍描边**（`strokeRiver`）：外层浅色描边（宽 ×2.4、alpha 0.35）+ 内层亮芯。
   一条 1px 实线在花掉的地形上**根本认不出来** —— 这是"河流看不清"的由来。
3. **由细到粗的绘制序**：追踪输出是"大流量在前"，照那个顺序画，细支流会**压住**它汇入的
   干流下游段（看着就是"主干忽然变细"）。现在按流量**升序**画，粗的永远最后落笔。
4. **河网合并**（默认开启，`coalesce`）：按流量降序认领，已认领的上游端点跳过 ——
   同一条干流不再被反复画很多遍。⚠️ **如实说**：这项在这份数据上的收益是"少了重复描边"，
   **不是"多了长河"**（最长河两边都是 111 世界单位）。
5. **`Straaled` 河序**（`order[]`，Strahler 逐点推）：逐点带上"这是几级支流"，供后续按级数
   分层渲染/筛选用。本轮只出口径，**没有**据此再加一道筛选（那会需要另一轮观感确认）。

### 2.5 要更长的大河，唯一的路

### 2.6 「源头高度」闸门做成了 UI（2026-10-14 第三轮补）

2.4 那张表说明：这份地形上**条数由"源头高度"这个闸门主宰**（默认 60 → 3 条；40 → 67 条）。
而在此之前这个值写死在 `TRACE_SOURCE_HEIGHT` 里 —— 用户看到"生成 3 条河流"时
**既不知道是被闸门卡的，也无从调**。这正是本项目反复踩的那一类缺陷：**能力存在但够不着**。

现在：
- 「自动河流」按钮**右边紧挨着**一个数字输入（`data-testid="river-source-height"`，
  title 写明"60 → 3 条、40 → 67 条"）—— 不藏进「更多」，因为它和"点一下自动河流"
  是同一个动作的两个参数；test_65 复核：主行仍是**恰好 6 个可见控件**，契约不回归；
- 状态栏回执**把闸门读数一起报出来**：`生成 N 条河流 · 闸门：源头高度 >60、离海 ≥2 格 · N ms`；

口径：`H[i] > sourceHeight` 才能当河源（**严格大于**，回执文案与之逐字对应）。
测试钉死的行为（`test_103` 新增一段）：**同一个输入上，松（0）必须比严（90）出更多条** ——
不比较就不知道那个输入框是不是摆设。实测（用例地形 75×75）：**0 → 3552 条、90 → 518 条**。

## A3、高度图分辨率：放大**不增加信息**，只让同一片地形走得更细

### 3.1 实测（同一份 desite 高度图，双线性放大后重跑追踪）

| 放大 | 格数 | 陆地格 | 离海最大 | 出图 | 中位长(点) | **最长(点)** | **最长(世界)** | maxFlow | 追踪 ms |
|---|---|---|---|---|---|---|---|---|---|
| ×1 | 9975 | 2506 | 11 | 57 | 4 | 8 | **111** | 15 | 132 |
| ×2 | 39485 | 10027 | 22 | 287 | 6 | 14 | **120** | 58 | 489 |
| ×3 | 88531 | 22593 | 33 | 643 | 9 | 19 | **110** | 121 | 1095 |
| ×4 | 157113 | 40129 | 44 | 1089 | 11 | 25 | **110** | 215 | 2437 |

**这张表是本文最重要的一张**：
- 「最长(点)」8 → 25（格子细了，点数当然多）；
- 「**最长(世界)**」111 → 120 → 110 → 110 —— **几乎不动**。

放大 4 倍 = 格数 15.7 倍、追踪耗时 18 倍，换来的是**同一条河被更细地走了一遍**，
以及**多出 19 倍的河条数**（地图更花，不是更长）。

### 3.2 那放大到底有什么用（真有用的两点）

1. **海岸线/山坡的台阶变小**：源网格 spacing 14.4 在 1900×1080 上每格约 3.6 屏幕像素，
   放大到 400% 时一格占满一屏。放大 2 倍后等值线不再沿原格子走方波。
   —— 这正是用户说的「地形模模糊糊」，**唯一的解药是格子变密**。
2. **河流的几何更细**：折线点距从 14.4 单位降到 3.6 单位，Chaikin 平滑后的曲线更贴地形。

### 3.3 性能：先算账，再动手

`utils/heightmapResample.js` 的 `estimateResampleCost()` 在**按下去之前**给出格数/内存/耗时档，
UI 把它显示在面板上（`data-testid="resample-cost"`）：

```
5,625 格 → 22,201 格（149×149，约 1.5 MB 内存，预计 22 ms 以内）      ← ×2（档位 fast）
5,625 格 → 88,209 格（297×297，约 5.8 MB 内存，预计 88 ms 以内）      ← ×4（档位 ok）
```

三条硬护栏（都在纯函数层，Node 单测守）：
- **倍数上限 8**：再大不会多出任何地形信息，只是格数按平方涨；
- **单次格数上限 400,000**：超了**拒绝**，并点名"更小的可行倍数是多少"；
- **不规则网格直接拒绝**（点数与行列不符时"猜一个行列"会让地形整体错位且不报错）。

### 3.4 平滑（同一面板）

「地形一块一块」的另一半。用**分离式盒滤波**（先横后竖，O(n·半径)），
**不复用** `heightMath.smoothHeightmap` —— 那个实现对每格全表扫描（O(n²)），
真实底图 26910 格 ≈ 7 亿次内层迭代 = **秒级到十秒级的主线程停顿**，而且它**零调用**。

实测：20000 格 / 半径 2 / 1 遍 = **3 ms**（Node 单测断言 < 500 ms）。

⚠️ 平滑**只改 `h`**：`temp` / `prec` / `biome` 是**派生量**，平滑完地形要另点「重算派生图层」。
顺手改掉气候/群系 = 一次静默的气候改动（本项目最忌讳的那类）。

## A6、顺手修掉的第三个缺陷：「Vault 监听」是个假开关

这条**不在用户的三问里**，是做全仓审计时抓到的（同批审计结论见第七节）。

`main/index.js:710/713` 早就注册了 `get-watcher-status` / `set-watcher-status` 两个 IPC，
但 `src/preload/index.js` **从来没有把这两个 channel 暴露给渲染层**，于是：

- 设置面板的「监听 Obsidian 文件变更自动刷新」勾选框**只往 localStorage 写一个布尔值**；
- 主进程的 `vaultWatcherEnabled`（`index.js:22`）是**硬编码 `true`、从不读配置**；
- 结果：**用户关掉也照跑**（假开关），而且重启后勾选态也不还原。

修法：preload 补暴露 + 勾选框的 change 处理器真的拨到主进程（`onVaultWatcherChange`）+
打开设置面板时把用户意图推一次。**如实交代**：主进程在窗口起来时已按默认值启动 watcher，
所以"用户上次关过"这件事在**打开设置面板之前**仍会多监听一段；要彻底解决得让 main 启动时
读 config（属 main 侧重构，本轮没做）。

守卫（`test_main_module_wiring` 新增 2 条，都是**源码判据 + 反向探针**）：
- 反方向断言：**注册了 `ipcMain.handle` 的通道必须有 preload 暴露面**
  （旧守卫只查"暴露了必须有注册"，查不到"注册了没人能调"这个方向）；
- 勾选框的 change 处理器必须真的拨到主进程（只写 localStorage 就是那个假开关的原样）。

实测：**57 个通道双向对齐**（注册 ↔ 暴露）。
