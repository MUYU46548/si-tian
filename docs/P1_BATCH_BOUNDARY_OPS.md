# P1 第三件：批量边界操作**可行性评估**（2026-10-13）

> v1.9 执行单 P1 的三件 = ① 框选多选 ✅ ② 压叠检测 ✅（2026-10-11 已落，test_93）
> ③ **批量边界操作可行性评估** ← 本文。
> 结论先给：**只有一类批量边界操作值得做**（共享边两侧同时重采样），其余四类的收益/风险比不划算，
> 理由写在下面，含本轮**实测数字**与**明确标注为推断**的部分。

---

## 一、先把判据定死：什么样的批量操作"值得做"

一次边界编辑要同时满足四条才算合格（前三条是本仓已有的硬口径）：

| # | 判据 | 谁在守 |
|---|---|---|
| 1 | **无缝**：相邻两省共边两侧不能裂开（缝 = 两边都不属于 = 凭空丢地） | `test_97` / `test_102` |
| 2 | **无压叠**：不能把 A 盖到 B 上（点选/上色/标签三处会互相打架） | `test_79` / `test_93` |
| 3 | **不串省**：没被点到的省份逐点不动 | `test_102`（真实数据实测） |
| 4 | **一条撤销**：一次手势 = 一条命令 | `test_102` |

判据 1 在司天里有一个**结构性前提**：省份各自独立，共边只是"坐标重合"。
所以任何"整体移动/重算几何"的批量操作，只要**只动一侧**，就必然违反判据 1。

---

## 二、逐项评估

### A. 批量顶点拖动（多选一批顶点一起平移）—— ✅ **本批已做**
- 做法：`utils/vertexSharing.js` 按坐标量化格找出**邻省的同位顶点**，按同一 Δ 一起平移。
- 实测（真实 415 省项目，`drill_p1_vertex_marquee.py`）：
  - 27067 个顶点里 **2332 个是共边顶点**（858 个共享簇）→ 前提成立；
  - 建索引 **34.6ms**（一次拖动建一次，按 terrain 引用缓存）；
  - 拖一次联动 **8 个省**（该省活动环上有 10 个共边顶点，全被选中）；
  - 全图净面积漂移 **0.03 / 634574**（5e-8 相对）；**一条 Ctrl+Z 全还原**。
- 风险：只认坐标不认拓扑 → 两侧**顶点数不一致**的边界段（一侧有中点、另一侧没有）配不到人，
  那段就是"没联动"（不是错，是如实没做）。**没有量过这种段在真实数据里占多少**（诚实交代）。

### B. 批量整体平移 / 缩放 / 旋转某个省 —— ❌ 不建议
- 成本：极低（对点集做仿射变换即可）。
- 但**必然**违反判据 1：整省挪开 → 与所有邻省同时裂开；缩一点 → 沿整条边界留一圈缝。
- 真要用，只有两种场合成立：① 该省是**孤岛**（`p1` 不与任何省共边，索引里查得到）；
  ② 用户明确要"把这块地整体挪走"（那是重画，不是修边界）。
- 建议：**不做**。若日后要做，先查"这个省的共边顶点数 == 0"，非零就明确拒绝并说明原因。

### C. 批量简化边界（减少顶点）—— ❌ 不建议
- 成本：中（`collapseCollinearXY` / `chaikinRing` 已有）。
- 风险最高的一类：简化一侧的顶点集 → 那一侧的形状变了，而对面**没变** → 缝；
  要把两侧一起简化，得先知道"哪几段是共边、对面哪几个顶点对应" ——
  即"共享边两侧配对"这个更细的活（见 E），收益却只是"少几个顶点"。
- 实测依据（间接）：真实数据里 858 个共享簇中 **只有 25 个是逐位相同**，其余是 1e-12 级尾差 ——
  说明这份底图的共边**本身就是不同来源拼出来的**，对"顶点数一一对应"不能想当然。
- 建议：**不做**。真要减顶点，用「描轮廓 (Y)」按边重画一遍（那条路自带邻省重算与面积守恒）。

### D. 批量吸附/对齐（把选中的顶点吸到网格、骨架或一条共线）—— 🟡 可做，但优先级低
- 成本：低-中（吸附判据已有 `resolveSnapPoint` / `conformToSkeleton`）。
- 价值：把"手工描歪的边界"对齐到 50px 网格或邻省骨架，属于**整理**类需求，不是"做不出来"的阻塞。
- 风险：把共边顶点吸到网格 = 那一侧动了、对面没动 → 缝（同 C 的问题）。
  正解仍是"两侧一起吸"，与 A 用同一份配对索引 —— 所以它是 A 的**自然延伸**，而不是独立功能。
- 建议：等 A 在真实底图上被用过一轮（用户是否真的需要"对齐"），再决定要不要挂上去。

### E. 共享边两侧同时重采样（给一条共边段同时插点）—— ✅ **推荐作为下一件**
- 要解决的真问题：**A 项结构性前提的缺口**。两侧顶点数不一致时：
  - 拖"有中点"的那一侧 → 对面没有同位顶点 → 那段留缝；
  - 反过来，用户想拖的是"整条边界"却只能抓到零散几个点。
- 做法（复用本批已有的层，不新写几何）：用 `buildCoincidentIndex` 找出一段共边的两端点
  （两侧都有的那两个），在**每一侧**按同一参数 t 插入同样的中间顶点（弧长比例而不是等分点数，
  因为两侧的采样密度可能不同），插完两侧仍是"坐标重合"的形态。
- 成本：中（纯函数 + 一条 undo；不需要布尔运算）。
- 风险：**弧长参数化的对应关系**必须只依赖"两端点 + 各侧的点列"，不能依赖顶点数
  （否则不同密度的两侧会插出不对应的点 = 新的缝）。这条要用 Node 单测把两个方向的对照都钉死。
- 判据：插点后 ① 两侧顶点数相等且逐位重合；② 面积不变（插点不改形状）；③ 一条 undo；
  ④ 未选中的段逐点不动。

### F. 共享边"拉直 / 平滑"—— 🟡 与 E 同源，可合并
- 拉直一段 = 删掉中段顶点、只留两端 → 就是 C 的局部版；平滑 = 移动中段顶点 → 就是 A 的批量版。
- 建议：**不单独做**。E 落地后，"拉直"用 E 之后手动拖（或者只留两端点）即可，不值一条独立命令。

---

## 三、结论（一句话版）

**本批已把"批量顶点拖动 + 共边联动"做出来了（A）；剩下值得做的只有 E（共享边两侧同时重采样），
它是 A 的补全 —— 因为 A 的"只认坐标"这一步在两侧顶点数不一致的边界段上天然配不到人。
B/C/D/F 不建议单独做：要么必然违反"无缝"（B/C），要么只是整理类需求（D/F），
收益都撑不起一个新的写口与一条新的回归链。**

## 四、本轮**没有**量到的（如实列）

1. 真实数据里"两侧顶点数不一致的共边段"到底占多少（要写一个扫描器才量得出来，本批没做）。
2. 拖动在**真机（带 GPU 的 Electron）**上的手感：本演练跑在 headless Edge 上，
   一次拖动 3.8s **绝大部分是整幅重绘**（415 省 × 3 帧），不是算法耗时（索引 34.6ms）。
3. E 的参数化在"两侧采样密度差 10 倍"的极端段上是否仍然只插出对应的点（只有推理，没实测）。
