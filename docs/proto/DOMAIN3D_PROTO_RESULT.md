# E-4 性能原型结论（2026-11-25）

> 一句话：**B 方案（域内真 3D + 合批）可行，技术风险清零。**
> 合批后渲染耗时是常数 0.30ms，与恒星系数量无关；逐对象版随数量线性增长。

---

## 一、这个原型只回答一个问题

当年搁置 E-4 的理由是"会显著放大性能与交互复杂度"。性能的具体焦虑是：
**一个星域几十个恒星系 + 航道 + 边界同屏，会不会掉帧？**

答案是**不会**，只要合批。

## 二、实测数据（headless Edge + SwiftShader 软件渲染）

同一份场景数据、同一个会话里量两遍（**对照组是必需的**：
只量合批版无法证明"是合批带来的改善"，也可能是机器本来就快）。

| 恒星系 | draw calls（逐对象 → 合批） | 渲染中位（逐对象 → 合批） | 加速 |
|---|---|---|---|
| **30**（A 档 120÷4 势力） | 68 → **3** | 0.500ms → **0.300ms** | 1.67× |
| **60** | 136 → **3** | 0.600ms → **0.300ms** | 2.00× |
| **120**（整个 A 档同屏） | 275 → **3** | 1.100ms → **0.300ms** | 3.67× |
| **300**（极端） | 685 → **3** | 2.100ms → **0.300ms** | 7.00× |

**关键读数**：合批版渲染耗时**恒定 0.30ms**，不随恒星系数增长。
30fps 预算 33ms，余量 99%。

## 三、口径踩的坑（这段比数据重要）

### 坑 1：帧时被 vsync 拍平 → 差点得出"合批没用"的错误结论

第一跑量出"合批 16.70ms / 逐对象 16.70ms"——两边一模一样，正好是 60fps 的 16.67ms。

**那不是"两版一样快"，是 rAF 被 vsync 拍平了**：`renderer.render()` 只花 0.3ms，
浏览器照样等到下一个刷新点才回调 → 量到的是刷新周期，不是渲染耗时。
在这个口径下"合批加速 1.0×"是**假的**。

修法：用 `performance.now()` 夹住 `renderer.render()` 本身，量**同步渲染耗时**。
两个口径一起报：帧时告诉我们"卡不卡"，渲染耗时告诉我们"有没有余量"。

> 📌 通用教训：**任何用 rAF 量耗时的探针，都要小心 vsync 拍平**。
> 空载时 16.67ms 是"没事干"，不是"正好 60fps 的性能"。

### 坑 2：等"结果齐了"，不等"某个 UI 动了"

探针第一版等 `verdict.classList.contains('show')` 判跑完，结果在合批那轮刚结束时就
以为跑完了，只拿到一半数据。改成等 `RESULT` 里**两个键都在**。

### 坑 3：模块作用域的变量，外部探针读不到

`const RESULT = {}` / `let SCENE_DATA` 在 ES module 里是模块作用域，
`cdp.eval("RESULT")` 直接 ReferenceError。必须显式 `window.RESULT = RESULT`。
同时把入口挂成 `window.__proto = { runAll, result, info }` ——
**探针不该模拟点按钮**（按钮文案会改、DOM 会变，挂函数稳定）。

## 四、副产品：一个纯函数地基

`src/renderer/src/galaxy/domain3dScene.js` —— 场景适配层，17/17 Node 单测。

它把"一个星域 + 成员恒星系 + 域内航道 + 边界"算成**合批友好**的扁平数组：

| 输出 | 形状 | 用途 |
|---|---|---|
| `stars.position` | `Float32Array(n*3)` | 喂 `InstancedMesh` / `Points`，一次 draw call |
| `lanes.position` | `Float32Array(段数*6)` | 喂一次 `LineSegments` |
| `borders[i].position` | `Float32Array` | 轮廓环（数量少，不强行合批） |
| `counts.drawCallsIfBatched` | 常数 3 | **验收用**：反向探针盯着它，退化就红 |

单测覆盖：合批结构 / 跨域与自环过滤 / 脏坐标跳过 / z 派生确定性 / 取景公式 / 源码闸门。

### 另两个被单测揪出来的真错

1. **`fitCameraFor` 的 aspect 算错了**：第一版拿 `max(spanX, spanY)` 当竖直跨度再除以 aspect
   → 宽 bbox 配宽画布时算出 1340ms 距离，实际只要 279，**白退 4.8 倍**（图小得看不清）。
2. **测试自己的假红**：源码闸门扫到注释里的 "Math.random" 就判违规。
   闸门自己也要守"别把注释当代码"。

## 五、相机：**正交投影**（2026-11-25 用户拍板，替换透视）

### 问题（用户原话）

> "很扁看不清，不如原来平面平铺。现在稍微远一点的东西就看不清。"

### 根因：不是调参问题，是透视投影的必然结果

透视下屏幕上大小 ∝ 1/距离 → 远处的星域天然更小、字天然更糊。
想看清远处只能拉近相机，拉近又看不全近处 → **永远是"扁 + 糊"**。

### 解法：正交投影

`refs/src/星域视图1.jpg` 可验证：**群星整张星图就是正交投影**，
远近一样大、一样清晰；只有飞进单个星系内部才切透视。

换成 `OrthographicCamera` 后：

| | 透视（改前） | 正交（现在） |
|---|---|---|
| 远处星域大小 | 明显变小 | **一样大** |
| 远处星名清晰度 | 糊 | **一样清晰** |
| 纵深表达 | 靠大小 | 靠遮挡 + 明暗 |

### 换相机带出的三个坑（都修了）

1. **缩放语义变了**：透视靠"拉远拉近"，正交靠 `camera.zoom` + frustum。
   照旧调 `minDistance/maxDistance` 会发现滚轮没反应。
2. **背景星场变成方块**：`PointsMaterial.sizeAttenuation: true` 在正交下不再衰减，
   `size` 被当**世界尺寸**用 → 20 多世界单位的方点。改 `sizeAttenuation: false` + px 值。
3. **自绘光晕 shader 的透视公式失效**：原来按 `300/dist` 算 `gl_PointSize`，
   正交下没有距离衰减 → 远景光晕全缩没。改成按"视锥半高 / 视口高"换算，
   并每帧 `syncOrthoUniforms()` 同步（滚轮改 zoom 后要跟着变）。

### 倾角也要压小

原来的 0.62（≈32°）把圆形星域压成明显椭圆。群星的倾角很小
（`星域视图1.jpg` 里领土轮廓接近正圆，只是略有透视）。改成 **0.28（≈16°）**。

> ⚠️ 倾角只影响"看起来多扁"，**不影响远近清晰度** —— 那个正交已经解决了。

## 六、布局也改了：从大圆环改成紧凑网格

第一版四个星域按大圆环排 → 围成一圈、**中间一大块空白**，截图里四个域分散在四角。

司天现状（`build/sample-galaxy/generated.png`）是**四个域紧挨着铺开**、占满画面。
改成 2×2 网格（`gap = 2.15 × radius`，刚好不压叠），场景跨度 5879 → **3736**。

## 七、三条口径已按用户拍板落地

| 口径 | 用户决定 | 原型落地 |
|---|---|---|
| ① 相机记忆 | 点进单系后返回**保持原相机** | 位置 + target 双存；`s4→s5→s6` 逐像素相同 |
| ② 星域边界 | **平面切片** | 半透明填充面（z=0）+ 轮廓线 |
| ③ 恒星系 z | **近似平面只做薄层** | `Z_THICKNESS = 0.06`（±54 / 900 半径） |

## 八、结论与建议

- **技术风险清零**：合批后渲染耗时与规模无关，30 系只用了 0.9% 的预算
- **三条口径已验证**：相机记忆逐像素可回、边界是切片、z 是薄层
- **可以做正式实现**：E-4 卡里 N1-N7 验收线一条没变，可照它开工
- **性能不是瓶颈了**，接下来的风险全在**交互与观感**：
  标签避让、边境光晕、点选命中、点进单系的过渡 —— 这些是经验活，不是算力活
