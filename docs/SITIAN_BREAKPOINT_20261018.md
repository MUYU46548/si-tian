## 1. 本轮（第十九修，只做了一半）停在哪

**停在一个测量的中途**：`scripts/tests/tools/_probe_save_block.js` + `_probe_jank_real.py __SAVE`。
它已经把结论量出来了，但**修法一行都没写**。读数（真实 `desite` 底图，200 省，载荷 **2.07MB**）：

| 场景 | 最长帧 | >100ms 的帧 |
|---|---|---|
| 静止（无编辑） | **18.2ms** | 0 |
| 一次编辑之后（防抖 800ms 到点） | **519ms**（出现在 1206ms 处） | 1 |
| 编辑后**一边拖鼠标一边等保存** | **596ms**（1414ms 处），次长 48.6ms | 1 |
| `exportCanvasToProject()` 自身 | **187ms** | — |
| 纯 `JSON.parse(JSON.stringify(载荷))` | **19.6ms** | — |

⇒ **每次编辑之后，主线程要被占住约半秒；而它恰好会落在"你还在拖"的时候。**
这解释了为什么"我把拖笔从 29ms/事件修到 2ms/事件"之后，手感**仍然会一顿**：
连续卡顿修掉了，**一次性半秒卡死还在**（而且比我上一轮估的 350ms 更狠）。

**下一个人从哪接**（不需要重新探路）：
1. 量化脚本已就绪：`python scripts/tests/tools/_probe_jank_real.py _probe_save_block.js __SAVE`
   （前提：把 `docs/mockups/desite.map` 临时拷进 `src/renderer/public/__real_desite.map`，跑完删掉）。
2. 已知的嫌疑与各自的判据：
   - `buildProjectPayload`（`store/geodata.js:1717`）**对 mapData / editor / baseMaps / scenarios
     各做一次 `JSON.parse(JSON.stringify(...))`** = 187ms 的主因；
   - 然后 `projectStore.saveProject`（`:606`）又对**整份载荷**做一次 `toIpcPlain`（≈20ms）+ `pushSnapshot`
     的 `deepClone`/`diffWalk`（`utils/projectSchema.js:551/693`）；
   - 最后 `ipcRenderer.invoke` 还要在渲染进程侧做一次 V8 结构化克隆（mock 下量不到，真机会再加一笔）。
3. 三个候选修法（按风险从低到高，**推荐先做 ①**）：
   - ① **"人在拖的时候不许保存"**：给自动保存加一道"交互闸门"（`beginStrokeBase` 已经在记录手势了，
     顺手暴露出 `isUserGestureActive()`；`scheduleAutoSave` 在闸门开着时顺延，设一个上限如 5s，退出前
     `flushSave` 兜底）。风险低、直接消掉"拖动中撞保存"。
   - ② **去掉重复序列化**：`buildProjectPayload` 的四次往返是为了**切断与响应式 store 的别名**
     （T2 那次数据事故的同源问题），不能裸删；但 `toIpcPlain(withSnapshot)` 那份可以对
     "刚由 `buildProjectPayload` + `pushSnapshot` 造出来的载荷"做**已证纯 JSON** 的快路径
     （dev 模式留一个 walk 断言，生产跳过）。省 ~20–40ms，风险中等。
   - ③ **把序列化挪出主线程**（分片/Worker）：收益最大、工程量也最大，留到"确实还卡"时再上。

## 3. 正视"抄都抄不明白"这条反馈（我的判断，不辩解）

我不认为这一轮是白做，但**暮雨的体感是对的，而且原因在我这边**：

1. **我修的是"我能量到的卡"，不是你感到的卡。** 我盯着"连续拖动每帧 29ms"一路修到 2ms，
   但真正让你觉得"还是卡"的是那次编辑之后 **596ms 的整块卡死**（今天才量出来）。**判据选错，
   功夫就白费一半** —— 这条我认。
2. **"参考现成绘图软件"我抄的层次太浅。** 我只抄了"预览=落库""橡皮"这两个**表层交互**；
   绘图软件真正撑住手感的三件事是：**分层缓存 + 增量重绘**（我抄了一半，只做手势期）、
   **持久化不上主线程**（我完全没抄 —— 这正是那 519ms）、**工具与数据解耦**
   （它那边是"笔迹→图元"的转换层，我们这里 200 省 / 24k 顶点的几何还在每帧现算）。
   换句话说：**我抄的是动作，不是架构。** 这就是"对着现成的东西抄不明白"的字面含义。
3. **"大代价扫库"这种打法的收益已经见底。** 本会话把大量预算花在"读旧文档 + 复现旧结论 + 补守卫"上，
   而每一次真正的用户可感改进都来自**一次现场测量 + 一个小改动**。所以下一阶段我建议换成：
   **先做竞品调研与目标重排（暮雨已计划），把"该像哪个软件"写死成几条可验收的目标**，
   再按"一条目标 → 一个探针 → 一个最小改动 → 一枚判据"的节奏推进，而不是继续铺文档与守卫。
