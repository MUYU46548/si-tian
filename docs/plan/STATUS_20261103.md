## 诚实：没做到的

1. **星域形态仍不像群星**：`layoutDomains` 已有 ring/disc/spiral，但 n≥8 时螺旋臂**读不出来**（领土半径 350 + 中心间距 760 把臂挤平）。要像群星得靠“星域数量上一个量级”或整幅美术托底，不是调参能解决的。
2. **涂归属松手 62ms 未达 50ms 口径**（本轮新发现）：**写口只占 3.3ms**，~59ms 在松手后的同步收尾
   （事件派发 + 重绘 + 回执）；且用户可感知的“落库”是 1.37s（两层防抖 + 写盘）。下一轮先砍那 59ms，
   再评估“落库中”要不要可见反馈。
3. **星云不按视口裁**：背景资产仍按固定 3200×3200 世界矩形铺，超大图幅导出会多画一块（视觉无问题）。
4. **国界只在共边处**画（跨海峡/飞地的“海上国界”没做）。
5. **示例星系四个星域大小偏斜**（5/19/49/3 颗）：参数照抄原型 SP-1025，为了保留“与原型对照”的基准，**没调**。
6. **六个浮层的“内容正确性”**（按钮该不该禁用、文案对不对）仍只靠人眼；自动判据管的是层级/遮挡/可读性/开关。
7. **`ScenarioMap` 的模板还有 1.9k 行**没拆。下一刀应是“浮层/面板组件化”，不是继续搬函数（函数已经搬空，剩下大头是模板与注释）。
8. **全量回归在长会话里会卡在 `test_21_brushes` 的第 6 步**（整张 heightmap 的 JSON 往返：页面侧
   `JSON.stringify(snap, jsonSafeReplacer)` 在累积了几十个用例的页面上耗时到几乎不返回；**单独跑 1/1 通过**）。
   本轮用“162 个一批 + `test_21` 单跑”把 163 个全跑绿；根因与修法（把该步的往返对象改成有上限的切片，
   判据不变）留给下一轮。**这不是产品缺陷，是测试用例的写法**。

## 下一轮最该做的三件（按性价比）

1. **砍涂归属那 58ms**：照 `build/owner-latency/<ts>/summary.md` 的拆账定位（写口 vs 事件/渲染）；
   顺带评估“落库中”要不要给可见反馈（1.37s 的静默期偏长）。
2. **模板组件化**：把六个浮层与右侧属性面板从 `ScenarioMap` 模板里挪成子组件（判据现成：
   像素基线 + `npm run test:visual` + `test_118`）。
3. **星域形态**：先攒够星域数量（或做整幅星云/星链托底），再谈螺旋臂 —— 现在调布局公式是白费。
