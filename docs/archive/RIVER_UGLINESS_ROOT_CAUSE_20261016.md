## 1. 根因（渲图实测，非猜测）

把两套河各自单独渲成 PNG（`scripts/tests/tools/_render_river_compare.mjs` → 见 `docs/assets/river-compare/`）：

| 图 | 内容 |
|---|---|
| `1-现状-自动河网.png` | 自动河网（1710 段）单渲 |
| `2-底图自带FMG河.png` | 自带河 160 条单渲 |
| `3-叠图-深色=自带_红=自动.png` | 叠图：**深色 = 自带，红色 = 自动** |
| `4-未平滑.png` / `5-先平滑再追踪.png` | 平滑前后对照 |

**叠图把话说死了**：深色（自带河）是**又长又弯、几乎贯通全岛的主干**；
红色（自动河）是**几百根短、直的小棍**，几乎全挤在海岸附近 → 这就是"恐怖感"。

**根因不是配色、不是线宽，是几何分辨率：**

| 指标 | 实测 |
|---|---|
| 岛宽 | ≈ **1700** 世界单位 |
| 高度图网格 | **133×75**，格距 **14.4**（FMG 的平滑河线密度是它的 ~10 倍） |
| 最长代表路径 | **140** 世界单位 = 岛宽的 **8%** |
| 段长中位 | **17.5** 单位 ≈ **1.2 格**（每段就一格多） |
| 代表路径条数 | 仅 **12** 条（1710 个段散在这一坨里） |

→ 在"一格 14.4 单位"的粗网格上追出来的水，**只能是短、直、放射状的**。
`riverTrace.js` 自己的注释（`:331-334`）也写明了这个两难：
只按原始高度 → 微洼地成终点（最长 10 格）；只按水位 → **一片放射状短支沟**（就是现在这样）。

## 2. 三条路线，全部实测过

| 路线 | 做法 | 实测结果 | 结论 |
|---|---|---|---|
| **A 追踪前放大** | `traceRivers({upsample:N})`（产品**已有**、但**零调用**） | ×2：河 12→116、段 1710→6342、最长 140→**110**；×3：河 405、最长 103 | ❌ **更碎、更乱**，最长反而变短 |
| **B 填洼** | 优先队列填洼后重追（原型） | 只抬高 **194/9975 格（1.9%）**，死水比例反而升 | ❌ 无效（这份地形几乎没有真洼地） |
| **C 追踪前平滑** | 产品的 `smoothHeightmapGrid` 先平滑 `h`，再追 | r=2 p=1：河 12→**29**、最长 140→**270**（**约 2 倍**）、中位 69→92 | ✅ **唯一有效的方向** |

**C 的代价（必须一起说）**：平滑会把山头压低 → **源头高度闸门会越来越难满足**。
实测 `r=3 p=3` 直接 **0 条河**（源头全被削没了）。
→ 平滑必须配**更低的源头高度闸门**，否则"平滑完一条河都没有"。

**回执长这样**（用户能看懂"为什么闸门变成 40 了"）：
> 生成 N 条河流 · 河网 M 段 · 闸门：源头高度 >40、离海 ≥2 格 · **已先平滑地形（半径 2）→ 闸门按 40 起算（平滑会压低山头，不降闸门可能一条河都没有）** · 123 ms

**测试**：
- Node 单测 +3：默认关时与旧路径**逐字段一致**、平滑确实拉长河道、平滑会改变源头数（**方向不假设**——我第一版写成"必定变少"→ 假红，实测 r2p1=1375 / r8p4=1845）；
- CDP `test_103` +8 条源码守卫、+1 条行为探针（**点真复选框** → 回执必须含「已先平滑地形」、闸门读数必须变 40、关回去后不许再出现）。

### 🔴 本轮的第二个"我错了"：测试装置自己的坑
行为探针第一版直接写 `sm.riverSmooth = true`（`setupState` 上的 ref），**产品行为是对的、探针却是假红**。
根因：同一文件里模板用裸 `riverSmooth`、脚本用 `riverSmooth.value`，直接赋 `setupState` 的属性能不能被脚本侧看见取决于解包口径。
→ 改成**点真的复选框 / 操作真的 `select`**（+ `await tick()`，本仓既有纪律）后立刻通过。
**纪律：CDP 行为探针要驱动真控件，不要直接改 `setupState` 上的 ref。**

## 3b. 🔴 最终根因：**数据源本身就没有长河**（导入链路已查证**没有降采样**）

暮雨要求"查导入链路是否降采样"。查了，结论是**没有降采样**，而且查出了比降采样更根本的东西：

| 检查 | 读数 |
|---|---|
| 原始 `.map` 还在吗 | ✅ `SiTian\backups\repair-basemap-20261011-220317\desite.map`（4.29 MB，`docs/mockups/desite.map` 同一份） |
| 原始网格 | **`cellsX=133  cellsY=75  points.length=9975  spacing=14.4`** |
| 原始 `cells.h` | **长度 9975**，值域 **0~100 整数**（前 12 个：`0,0,0,0,1,2,2,2,1,1,1,2`） |
| 项目里现存 | `cellsX=133  cellsY=75  count=9975  points=9975  h.length=9975` |
| 判定 | ✅ **格数/高度长度一字不差 → 导入链路没有降采样** |
| `.map` 自己的元数据 | **`cellsDesired: 10000`** ← Azgaar 的**最小档**网格 |

**所以「长河」不是没做，是这份数据里没有**：

- 岛宽 ≈ **1700** 世界单位，高度图只有 **133 格宽**（1 个陆地像素 ≈ 14 世界单位）
- 陆格 ≈ 2950 个；**单格最大汇流累积 = 22 格**（`traceRivers` 的 `segMaxFlow=22` 与手写标准水文管线**完全一致**）
- → 最长可能河道 ≈ **316 单位 ≈ 岛宽的 19%**，而且必须从岛脊一路直下（这份高度场高度差均值只有 **8.91**，全是 1~2 格的微坑）

**为什么自带河（FMG）那么好看**：FMG 的河是 Azgaar 用它内部的**浮点高程**（`cells.h` 之外的完整高程场）生成的；
存进 `.map` 的 `cells.h` 只是**取整到 0~100 的粗副本**。也就是说：**这份 `.map` 里根本不存在能生成长河的原始数据**。

**推论（据实说）**：任何算法都无法从这份 `cells.h` 造出长河。
要长河只有两条路，**都不在"改算法"范围内**：
1. **在 Azgaar 里重开一张更高分辨率的地图**（`cellsDesired` 调大，如 100k）+ 导出 `.map` 重新导入；
2. **直接以底图自带的 160 条 FMG 河为河网**（这正是暮雨自己认可的「只画底图自带……逻辑没问题」）。

→ **建议把「自动河流」定位成"底图没有自带河时的兜底"**，而不是跟 FMG 较劲。

### 🔴 本轮否掉的三条路线（都实测过，别再试）
| 路线 | 读数 | 结论 |
|---|---|---|
| 追踪前**放大** ×2/×3 | 河 12→116→405、最长 140→**110→103**、代表路径 1058 条 | ❌ 更碎 |
| **填洼** | 只抬高 194/9975 格（1.9%） | ❌ 这份地形几乎没有真洼地 |
| 追踪前**平滑** | 无更低邻居的格 12.4%→**5.4%** ✅，但**高度差均值 8.91→3.20**（地形被压平） | ❌ 治了"坑"却毁了"谷"，只会长更多短毛刺 |
| **标准水文管线**（填洼→D8→汇流累积） | 最大累积 **22** 格（与现状相同） | ❌ 与现状同上限 —— **证明瓶颈是数据不是算法** |

⚠️ **算法本身是好的**：在**理想圆锥岛**上（`_probe_ideal_terrain.mjs`）代表路径中位 **265** 单位（岛半径 460）、
**80.6%** 的段 flow>2（真树枝状汇流）；带一条谷时 flow 最大到 **171**。**换成真实粗网格就只剩 22。**

## 4. 我**没有**改的（仍在计划里）

- **只做可读性整理**（把 flow=1 的短棍画淡/画没）—— 没做（改画法会动观感默认值）。
- **让自动河只补自带河没有的地方**（按自带河做排斥带）—— 没做（改动范围最大）。
- 产品**没有**把平滑做成"看地形自动决定"：仍是用户勾选。平滑的收益/代价依地形而变
  （真实底图 `r=3 p=3` 会 0 条河），自动化的风险是"悄悄把用户的河弄没"。
