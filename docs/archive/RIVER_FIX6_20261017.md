## 1. 逐条根因（都用截图/像素实测，不是猜的）

### ① 「一堆点，而不是线」——点数由**拖动时长**决定

真机实测链路：收点间距 6 屏幕像素 → 一条横穿屏幕的笔迹约 120 点 →
`Chaikin 2 轮`（每轮点数 ×2 减 1）→ **约 480 点**，而屏幕上那条河只有约 700px 长
→ **节点手柄间距 < 2px** → 几百个"深色圆 + 浅色描边"的手柄糊成一条点线。

🔴 而且这一条**我上一轮自己埋的**：我为了"可发现性"给每个节点画了手柄，
却没限制点数 —— 两个决定合起来就必然是这个结果。

**修法（两半都做，缺一不可）**：
- **点数受控**：新增纯函数 `fitPolylineToCount(points, target, {minCount, maxCount})` ——
  按**弧长**均匀取样把笔迹压到目标点数（端点逐字保留、只挑原点不插值）。
  目标 = 弧长 ÷ 期望间距（18 屏幕像素），夹在 `[6, 72]`；Chaikin 随之只跑 **1 轮**。
- **手柄有闸门**：`nodes.length ≤ 120` 且 `cameraScale ≥ 1.2` 才画全部手柄，
  否则**只画"活动节点"那一个**（手柄是给"我要拖某一个点"用的，不是给"看这条河长什么样"用的）。

**实测**（真鼠标事件画一条横穿画布的河，zoom=0.138）：
修前 480 点 / 间距 <2px → 修后 **64 点 / 最小间距 7.7px / 平均 15.2px**，手柄闸门 `showAll=false`。

### ② 「性能极其严重，还不能防用户乱画」

- 采点间距**跟着缩放走**：`max(12 屏幕像素, 2 世界单位)` —— 以前是固定 6px，
  放大后等于"每个像素收一个点"，而那些点在落库前**都会被压成 40 个控制点**，纯浪费。
- **笔迹上限 `RIVER_MAX_DRAFT_POINTS = 600`**：到顶就**明确说一句**并停止收点
  （之前长按慢拖/画圈可以把内存与每帧采样成本顶到天花板）。
- 落库阶段**先压点数再平滑**（见 ①）：平滑成本从 O(点数 × 迭代) 降到常数级。

### ③ 「色差依旧」——**第四处**颜色，而且每修一处就把别处变成异类

这条已经写过三遍教训，还是漏了：

| 时间 | 我做了什么 | 结果 |
|---|---|---|
| 2026-10-15 | `drawRiverPaths` 写死 `#5d97bb` → 收口到 `RIVER_COLOR`（`#3B82F6`） | 手画河画成 `#3B82F6` |
| 2026-10-16（第五修） | 发现**真正画出来的**自带河是 `#5d97bb`，而 `RIVER_COLOR` 从没被画出来过 → 自动河改对齐 `#5d97bb` | **手画河成了唯一那个用 `#3B82F6` 的** |
| 2026-10-17（本轮） | 用户截图：同一条河一半 `#5d97bb` 一半 `#3B82F6` | 这就是本轮 ③ |

**修法（这次是真的收口）**：
- `utils/riverRender.js` 新增 **`RIVER_DRAW_COLOR = BASEMAP_RIVER_COLOR`（`#5d97bb`）** ——
  **全图唯一的河色**；`RIVER_STROKE` 也指回它。
- `RIVER_COLOR`（`#3B82F6`）降级为**数据里的默认值**，**不再出现在任何描边路径上**。
- `ScenarioMap.vue` **不再 import `RIVER_COLOR`**（有源码守卫；导入河也不再读数据里的 `color` 字段来描边 ——
  老数据里存的可能是旧的 `#3B82F6`，渲染时必须忽略它）。

**实测**：河身中段采样 5 点，与 `#5d97bb` 的最大通道偏差 **1**（`allRiverColor: true`）。

### ④ 「不会弯吗？不会有粗细变化吗？」——几何是格心直连 + 单一线宽

- **不弯**：段是"格→格"的直线，几百根直线拼起来就是"小棍拼的河"。真实河流**没有直段**。
- **不粗**：手画河此前是**一个线宽画到底**（`c.lineWidth = px(1 + width*2)` 一条路径描完），
  形状再对也像一根管子。

**修法（三层，全部走共用纯函数）**：
- `catmullRomPoints(points, subdiv)` —— 折线 → **穿过控制点的曲线**（端点逐字保留；
  每段固定 `subdiv` 个点，所以成本可控）。手画河用它画整条；自动河**逐段**用一个
  垂直偏移的控制点变弧（`quadraticCurveTo`，幅度 = 段长的 12%，
  且**夹屏幕上限 1.8px**，否则放大后河会缠成意大利面）。
- `taperWidths(count, headW, mouthW)` —— **源头细 → 河口粗**，指数 **1.6**。
  🔴 我第一版写的是 `t^0.35`（< 1）—— 那个方向**正好相反**（起步就冲到半宽、之后几乎不变），
  单测里"中点必须比线性细"这条把它当场抓住（`0.35` → 中点 8.06、`1.6` → 中点 3.97）。
- 手画河的宽度**屏幕像素下限 1.6px**：底图可以缩到 14%，那时 `width=1.6` 世界单位
  只有 **0.22 屏幕像素** —— "在 100% 下多粗"毫无意义，**判据只能是屏幕像素**（第四次强调）。
- 顺便加了**岸线**（比水面深一档的细描边 `RIVER_BANK_COLOR`）：河不再"发飘"，而是嵌进地形。

### ⑤ 「一堆废话文本」——状态栏被我的实现细节占满

原来点一次「自动河流」，状态栏会铺出两行：生成条数 + 河网段数 + 丢弃数 + 跳过源头数 +
闸门读数 + 河长上限的长篇解释 + 平滑说明 + 耗时 + 两套河并存的建议 + **画布被压矮**。

**修法**：**一行结论 + 悬停看详情**。
- 状态栏只剩：`生成 N 条河流 · 河网 画/总 段（只画河道） · 闸门 源头高度 >60 · XXX ms · ⚠️ 长河受限（悬停看原因）`
- 那些"读一次就够"的长解释（为什么长河受限、两套河为什么并存）进 `riverTerrainAdvice` 的 tooltip。
- ⚠️ 但**闸门读数与平滑回执必须留在这一行里** —— 它们是"参数够不够得着"的证据
  （`test_103` 有守卫：回执里没有读数 = 用户会以为"河本来就少"）。

### ⑥ 参考图（省份边界 / 地形 3D / 河流走法）—— 两件已做、一件没做

参考图（EU4 风格真实世界地图）那种观感是三件事叠出来的。你选了**「两个都做」**，所以本轮把前两件也做了：

**A. 省份边界（第七修）**
旧实现是**逐省一遍**、普通省用 `rgba(141,138,130,0.6)` @**0.6px**。两个真毛病：
- **半透明 + 逐省重描** ⇒ 两个省的**共边被描两次** → 共边比独边深 ⇒
  同一张图上边界深浅不一（观感发灰发虚）；**它不报错**，只是"看着像没画干净"。
- 0.6px 在 1080 宽画布上几乎看不见（真实地图上省界是看得见的深色线）。

现在 `drawProvinceBorders` 分**两遍**：第一遍画所有省的普通边界
（**不透明** `BORDER_COLOR` @1.1px —— 不透明就没有"共边叠加变深"的问题），
第二遍才叠选中 / 多选 / 合并目标。顺手收口一处**双源**：画布以前写死一个灰，
而 SVG 导出用配色单源 `BORDER_COLOR` —— 同一张图**导出与画布边界颜色不一致**。
现在两处同色，导出线宽/不透明度也同步（0.6/0.6 → 1.1/1.0）。
**实测**：画布上边界色像素 2247 个（旧口径那一档几乎数不到）。

**B. 地形 3D 表现（第七修）**
此前只有**分层设色**（高度靠颜色表达）。真实地图让地形"立起来"靠**阴影**：
同一颜色带上，朝光坡亮、背光坡暗。新增 `heightmapRaster.buildShadeMap(h, cols, rows, {shade})`：
- 坡向由**中心差分**求（最省事、无方向偏差）；
- 光照 **NW**（制图惯例：光从左上；从右下会让凸起读成凹陷）；
- 明暗除以**本幅图的高度标准差**（按本分布归一化 —— 第五次强调；平缓地形不会被放大成噪声）；
- **海格不投影**（水面是平的）；海岸相邻格按自身高度处理（避免一圈黑边）；
- 输出逐格乘子（夹在 0.55~1.45），渲染时与颜色**共用同一套双线性权重**；
- ⚠️ **只对「陆海底色 / 地形高度」两档生效** —— 温度/降水是**专题图**，
  加阴影会把数值读成地形（错口径）。有判据守这一条（`tempUnaffected: true`）。

UI：图层行加「立体」勾选框（`data-testid="terrain-shade-box"`），**默认关 = 零行为变更**；
缓存键含开关与强度（否则"勾了没反应"—— 本项目老毛病），`watch` 列表也补了它（漏了同样没反应）。

**实测**（山脊/山丘地形，开关前后逐像素）：

| 强度 | 变化像素 | 占比 | maxDelta |
|---|---|---|---|
| 1（默认） | 73783 | 10.2% | 18 |
| 1.8 | 123719 | 17.0% | 32 |

⚠️ **代价必须说清**：我们的高度图**可能是粗网格**（真实底图 133×75 / 间距 14.4），
阴影会跟着粗（放大后能看出格子台阶）。**那是数据粒度，不是渲染问题** ——
与"长河不存在"是同一个瓶颈。要细阴影就得在 Azgaar 里开更高分辨率重导。

**C. 纸纹** —— **没做**。真实地图的"纸感"来自纸张纹理叠加，与地形数据无关；
本轮只做了"阴影"这一半（那是"3D 感"的主因）。

## 1.5 性能：量出真实数字再动手（用户点名「性能问题极其严重」）

量尺：`scripts/tests/tools/_probe_perf.js` / `_probe_perf_stages.js`（真机、75×75 底图 + 全量自动河网）。

**逐层拆帧**（1080×673 画布，120 次取平均）：

| 阶段 | 单次耗时 |
|---|---|
| 背景 / 高度图栅格 / 省份 / 标签 / 小地图 | 各 **0.01ms** |
| **河网绘制（自动河）** | **6.45ms** ← 全部成本都在这里 |
| 整帧（无自动河） | 0.03ms |
| 整帧（有自动河） | 6.48ms |

**拖动时的真实手感**（画一条手画河，40 次 mousemove）：
修前 **6.61ms/事件**（每次移动都同步重画整帧，一半帧预算浪费在"重画上一帧已经画过的"）
→ 修后 **0.03ms/事件**（约 220×）。

**怎么修的**（第七修补正过位置，见 3.8）：
1. **帧合并（只挂在高频手势上）**：新增 `renderCoalesced()` —— 同一帧最多重画一次，
   被**河流拖笔采样 / 拖节点 / 平移缩放**这几个一秒几十次的手势显式调用。
   🔴 `render()` **本身保持同步语义**（这一点我一开始改错了，见 §3.8）。
2. **采点间距跟缩放走** + **笔迹上限 600 点**（见 ②）—— 从源头少产生无用的点。
3. **先压点数再平滑**（见 ①）—— 平滑成本从 O(点数×迭代) 降到常数级。

**修后实测**：单帧（有自动河）仍 6.58ms，但**拖动每事件 0.06ms**（约 110×）——
因为合并只发生在"同帧重复"，而重复正是拖动时的常态。

⚠️ **一条没有改善的**：自动河那 6.45ms 本身（线段数量降 90% 后仍是 5.73~6.04ms，
说明成本在"每段一次 Canvas 描边调用"的固定开销上，不在段数）。
它只在用户点「自动河流」之后才存在，所以要再压得把河网**合并成一条路径**批量描边
（代价是失去逐段变宽）—— 那是取舍，留给你定。

## 2. 自动河的"恐怖谷"根因（本轮最意外的发现）

用 `_probe_auto_river_visual.js` 把自动河**放大到 100% 渲成图**才看清：
它不是"几根难看的河"，而是 **一整片平行斜线网格** —— 因为段是"每个能到海的陆地格一根小棍"：

| 数据 | 段数 | 段汇流分布 |
|---|---|---|
| 圆丘 121×121 | **11225** | p25=2 / p50=12 / p75=27 / p90=45 / max=136 |
| 斜地形 75×75（test_103 用） | **3750** | p50=**2** / max=**1275** |

**修法**：`pruneRiverNetwork(segments, threshold)` —— **按流量剪枝，但保留拓扑**：
① 超过闸门的段留下；② 流量小、但**下游被留下**的段也留下（否则干流半途断掉）；
③ 扫两遍把整条链传下去。

🔴 **闸门必须按分布取分位，不能按上界取比例**（我在这里栽了一次）：
第一版写 `segMaxFlow × 0.25`。圆丘上还行，但在**真实分布**上直接崩 ——
那份数据 `p50=2`、`max=1275`（极端长尾），0.25×1275 = 319 → 3750 段只剩 **26 段**（0.7%），
画布上几乎什么都没有（回归 `test_103` 当场抓住："画布上找不到河色像素"）。
改成 `riverFlowGateByQuantile(segments, 0.12)`（留流量最高的 12%）之后，
同一份数据留 **633 段**、圆丘留 **748/4500 段**。
🔴 **教训的完整版：归一化的对象是分布，不是最大值**（第四修那条"绝对数字会失效"的加强版）。

外加：河网最细线宽从 0.7px 提到 **1.2px**（0.7px 在 100% 缩放下几乎看不见），
并按"一格在屏幕上还有多少像素"自适应（格子 < 6px 时抬到 2.2px，避免布纹）。

## 3. 本轮我自己的两个 bug + 一次事故（留档）

### 3.1 `pruneRiverNetwork` 的格匹配用浮点字符串 → 拓扑链断掉

第一版拿 `` `${seg.x0},${seg.y0}` `` / `` `${seg.x1},${seg.y1}` `` 当"格"的键，而格心是**浮点坐标**
（spacing 14.4 → 0.1、14.5、28.9…）——上游段的 `x1,y1` 与下游段的 `x0,y0` 数学上相同、
**字符串未必逐字节相同** → 匹配失败 → 只剩强段（3750 → 26）。
**它不报错**，只是"有河但很稀"。现在量化到 0.01 世界单位（远小于格距、远大于浮点噪声），
单测里专门用带小数的坐标守这一条。

### 3.2 `taperWidths` 的指数方向写反（`t^0.35` 应为 `t^1.6`）

见 ④。**是单测抓住的**（"中点必须比线性细"），不是我看出来的。

### 3.3 🔴 事故与**我关于它的错误结论**（两次留档，第二次是我误判）

**事故本身**：我用 PowerShell 的 `Get-Content`/`Set-Content` 去改含中文的源文件。
这个坑我踩了四次：
- 前三次：Node 单测文件被搞成 CP936 乱码 / 被加上 BOM（`SyntaxError: Invalid or unexpected token`），
  每次都用编辑器工具整篇重写修回；
- 第四次：`test_103_auto_rivers.py` 出现乱码。

**我的错误结论**：我据此写下"该文件已被不可逆毁坏、需要整篇重写"，并据此派了一个重写任务。
**子代理按字节核查后推翻了它**，我随后自证：
```
test_103_auto_rivers.py: bytes=56400  bom=False  utf8=True  U+FFFD=0  汉字=5654
其余 scripts/tests/** 全量扫描：0 个文件有编码损伤
```
—— **文件一直是好的**。我看到的乱码有两个来源叠在一起：
① **终端渲染假象**（PowerShell 把 UTF-8 字节按 GBK 显示，`git`/`Select-String` 的输出都会这样）；
② 期间一次 Python 写盘把字节**修回了**合法 UTF-8（我误以为它在继续损坏）。

🔴 **这一条的教训比事故本身更重要**：
- **判"文件坏了"必须按字节判，不能按终端观感判**（`b.decode('utf-8')` + 数 `U+FFFD` + 数汉字）。
  我因为看了一屏乱码就宣布"不可逆毁坏、要整篇重写"——**那会白白引入一次大重写的风险**。
- **纪律（仍然要守）**：不要用 shell 读写含非 ASCII 的源文件（前三次的乱码与 BOM 是**真的**）。
  但由此得出的结论要止步于"用编辑器工具改"，**不能升级成"文件已毁"**。

**当前状态**：`test_103` 由子代理修两处**真缺陷**（不是重写）：
① "自带河隐藏"段量错了对象（用自动河的帧差去判导入河在不在 → 2~3 条断言永远不可能过）；
② "平滑开关"段被整段复制了两遍。

### 3.4 另一条反复踩的：页面跑着旧模块，我却去查"产品缺陷"

改了源码后，普通 reload 可能仍执行**改之前**的模块（Vite 缓存 / HMR 时序）——
我为此白查了一轮"节点拖不动"（其实是页面还是旧代码）。
现在 `_lab.py` 的 `run` 带 `?lab=<时间戳>` 破缓存。
**纪律：探针出结论之前先确认"页面跑的是刚改的那份"**（探针里加一个标记，如 `typeof sc.worldToScreen`）。

### 3.5 探针自己算错坐标（两次）

- `sc.cameraX + wx * sc.cameraScale` —— `sc` 是组件实例代理，**ref 不会在那里解包** →
  变成 `[object] + wx * [object]`。为此在产品侧加了 `worldToScreen()`（与 `screenToWorld` 互逆），
  探针与产品从此走同一个换算。
- 切到河流工具会多出一行「河流编辑」→ 工具栏变高 → 画布下移 40px → 旧 `getBoundingClientRect()` 失效。
  **每次交互前重读 rect**（已写进用例注释）。

### 3.6 🔴 第七修我自己埋的一个**运行时崩溃**：漏 import 两个常量

`riverWidthsFor()` 用了 `RIVER_WIDTH_MIN` / `RIVER_WIDTH_MAX`（定义在 `utils/rivers.js`），
而 `ScenarioMap.vue` **没有把它们加进 import 列表**。

🔴 **为什么这类 bug 特别危险**（值得单独记一条）：
- **Vite / esbuild 都不查"未声明标识符"** —— 它不是编译错误、不会在构建时报，
  而是**只在该函数被执行时**抛 `ReferenceError`；
- 于是症状是「**河画了但看不见**」：`drawRiverPaths` 一跑就抛，渲染护栏 try/catch 吞掉，
  **连续 3 帧**失败才暂停整块画布 —— 用户看到的是"画了没反应"，而不是任何明确的错误；
- 而且它**只在图上有手画河时才触发**（底图上没有手画河时那行根本不执行）→
  常规用例、甚至我自己的截图流程都可能照常全绿。

**是 `scripts/tests/unit/test_undefined_identifiers.js`（全仓扫描器）当场抓到的**：
`发现 2 个未声明标识符：RIVER_WIDTH_MIN / RIVER_WIDTH_MAX`（193 个文件全扫）。
它的**反向探针**也证明它抓得住（"未声明标识符必须被报出 — 1 条，名字正确"）。
**教训**：新增"用外部常量"的代码时，**必须跑一次全仓扫描器**，不能只跑相关用例 ——
相关用例可能压根不经过那条分支。

### 3.7 判据失败必须**带现场**（子代理一次就指出真因）
子代理的 c 段像素探针读数恒为 `None`。第一次它猜"画布 resize / `IndexSizeError`"——**猜错了**；
第二次它加了 `_probe_err()`（把 `stage / err / stack / 宽高 / saved(rivers,segs) / renderNow 有无`
一起写进红色文案），**一次就指出真因**：那整段探针的 `__SC__` 占位符**没有被 replace**
（字符串结尾漏了 `.replace('__SC__', SC)`）→ `const sm = __SC__` 直接 `ReferenceError`。

**纪律**：判据失败时"回一个 None"是最坏的输出 —— 它把现场全丢了，
后来人只能重跑一遍去猜。**失败必须带回现场**（这一条与我们既有的"拒绝必须有回音"是同一条纪律）。

### 3.8 🔴 我把 `render()` 全局改成异步 —— 5 个用例同时红（我自己踩的最贵一个）

为了性能，我把 `render()` 全局改成"同帧只画一次、后续推迟到下一帧"。结果全量回归
**101/106**，5 个用例同时变红，共同点是**"改数据 → `render()` → 立刻取像素"**：
`test_20`（Alt 临时直线生效 → 差分 0）、`test_53`（护栏读不到错误、3 帧不暂停）、
`test_61`（打开省份工具后画布为空）+ `test_73`（势力标注不跟着改）、`test_90`（两态画面相同）。

🔴 **根因不是"测试写得脆"，而是 `render()` 的语义是同步** —— 全仓几十处调用都依赖它。
**为一个局部优化付全局语义代价是错的。**
修法：`render()` **恢复同步**（语义不变）；新增 `renderCoalesced()`，
**只被真正的高频手势显式调用**（河流拖笔采样 / 拖节点 / 平移缩放）。
修后：`test_20/53/61/73/90/106` **6/6 回绿**，且拖动性能仍是 **6.58ms/帧 → 0.06ms/事件**。

⚠️ 这条也解释了为什么"改公共 API 的行为"必须跑**全量**回归：那 5 个用例单看都不像与河流有关。
