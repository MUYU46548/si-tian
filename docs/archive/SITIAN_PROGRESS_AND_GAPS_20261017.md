## 1. 三个模块的现状（按"能不能用"分，不按"做了什么"分）

### 1.1 宇宙与星系地图（对标《群星》）

**本轮完全没碰。** 我没有证据说它可用或不可用 —— 这几轮全部资源都投在河流与地图几何上。
已知的结构事实（来自仓库文档，非本session验证）：

- 七层视图链已实现：world → domain → system → system_detail → planet → area → interior
- `GalaxyMap` / `SystemView` / `SystemDetailView` 均 >1500 行
- 有航道（hyperlane）、实体树、项目文件承载

**未验证的关键问题**（下一轮必须先回答）：
- 星系图有没有"可玩"的对象？现在能不能在星系之间移动舰队/施加影响，还是只有一张可看的图？
- 与《群星》的差距是**表现层**（星图渲染）还是**系统层**（时间推进、势力、AI、事件）？
- 如果只是表现层差距，工作量是周级；如果要系统层，那是另一个量级的产品 —— 必须先把这一点钉死。

#### 1.2.1 自动河流：已经改到什么程度，还差什么

**已解决（有实测）**：

| 问题 | 之前 | 现在 |
|---|---|---|
| 画法是"逐格小棍" | 一格一段、独立描边、无线可平滑 | **沿流向链**画曲线（593 链→99 链，中位 17 格，平均转角 23°→7°） |
| 河伸进海里 | 段级裁剪漏末端 | **链级硬裁剪**：河色像素落海 0.2%（31/13444） |
| 拖动卡顿 | 每事件 6.61ms | **0.06ms/事件**（帧合并只挂高频手势） |
| 河太细 | 河口 2.7px 且调不上去 | 8.4px@100%，1.4× 缩放下仍保 1.8px |
| 无高度图就没有河 | 直接拒绝 | **按轮廓推演**（离岸距离 + 三段旋转噪声 + priority-flood 填洼） |

**仍不达标（用户实测）**：
1. **支流汇流不够复杂**。当前底图（外部导入 133×75）单格汇流上界只有 **22**；
   推演地形能到 **309~429**，但推演地形本身"不像真地形"（见下）。
2. **推演出来的地形结构粗糙**：只有"内陆高、海岸低 + 噪声"，
   **没有山脉走向、高原面、裂谷** —— 而这些正是用户自己调出来的那份高度图里有的。
   用户评价：「自动生成的高度图还不如我原来自带的高度图」。**我接受这个判断。**
3. **梳齿现象**（局部密集平行线）仍未彻底消除。根因已定位：
   ① 完美光滑高度场（如圆锥）在数学上只能产生平行流；
   ② 值噪声的**轴对齐格点**会在高频段印出规则斜槽网（"烤牛排"，已用逐频段旋转坐标缓解，
      但只是缓解，不是根治）。
   真正的根治需要**流向路由层的平局打破**（tie-breaking）或更高保真的地形生成，
   两者都不是"调个参数"能解决的。

#### 1.2.2 本轮踩过的坑（都是"假保证"型，必须写进规划）

| # | 坑 | 后果 | 教训 |
|---|---|---|---|
| 1 | 判据放在 `onCanvasClick` | 真机手抖不发 click → **选中功能等于不存在**，而 `test_110` 全绿 | 判据必须模拟**真人操作**（含抖动/无 click） |
| 2 | 按钮显示条件含 `!baseMapHasHeightmap` | **正好在用户找它时把它藏了** | 条件式隐藏 = 等于没做 |
| 3 | `synthesizeBaseMapTerrain` 绕过 `execute()` | **撤销栈被搞坏，用户全程无法撤销** | 写口必须走 `execute(undo/redo)`，`test_54` 只查登记不查写法 |
| 4 | `render()` 全局改异步 | 5 个用例同时红（依赖"改完立刻出像素"） | 公共 API 语义不能为局部优化让步 |
| 5 | 漏 import 两个常量 | 手画河渲染必抛（症状"河画了但看不见"） | Vite 不查未声明标识符；靠全仓扫描器 |
| 6 | 浮点字符串当格键 | 剪枝从 3750 段剩 26 段 | 量化键 |
| 7 | 值噪声轴对齐 | 整片"烤牛排" | 逐频段旋转坐标 |
| 8 | 我误判 `test_103` 被编码毁掉 | 差点白做一次整篇重写（实际文件完好） | 判"文件坏了"必须按字节，不能按终端观感 |

### 1.3 历史剧本（对标 EU4 的"开发者预设剧本选择"视图）

**本轮只碰到两处**，都不是模块能力本身：
- 新建剧本对话框的 `placeholder` 里**写死了真实世界观专名**（「乐园星历」）→ 已改，新增 `test_107` 扫描；
- 剧本「元信息可编辑 / 标注标记可删」是**上一轮**修的（`test_87`）。

**按用户的判断，这个模块"没有任何东西是能用的"。** 我不知道具体断在哪一环，
但从代码结构能看出的**结构性风险**（下一轮必须验证）：

1. **剧本 = 时间切片 + 归属快照**（`ownership` / `changeEvents` / 切片点 / 版本）。
   这是一套**数据模型**，而不是一个**视图**。对标物（EU4 选剧本界面）的核心是
   「一排书签卡：年代 + 地图缩略图 + 一句钩子文案 + 开局态势」，
   我们现在有数据、但**没有那个视图**。
2. **入口是"历史剧本"按钮**，进去是地图编辑器 + 一条剧本管理列表。
   对用户来说那不是"选一个剧本开始玩"，而是"进入一个编辑器"。
3. **三个模块之间没有闭环**：星系 → 行星 → 区域 → 剧本，每一层都停在"能编辑"，没到"能运行"。

## 3. 给下一轮深度规划的输入（我认为必须先回答的五个问题）

1. **三个模块各自的"最小可用"（MVP）定义是什么？**
   例：星系图 MVP = 能选中星系 → 看到行星列表 → 能进行星；
   行星图 MVP = 能画大陆 → 有地形 → 有河 → 能存能开；
   剧本 MVP = 能看到预设剧本卡 → 点进去 → 地图按该年代渲染。
   **没有这层定义，"修了几百轮还是不能用"会继续发生。**
2. **对标产品的差距在"表现"还是"系统"？** 两条路的工作量差一个数量级，必须一次钉死。
3. **谁是"能用的判据"？** 现在判据全是我写的，而我写判据时用的心智模型与用户的不一样
   （本轮 8 个坑有 5 个是"判据绿、用户用不了"）。是否需要**用户视角的验收脚本**（按用户实际操作路径，不看源码）？
4. **要不要砍**？三个模块并行修 = 每个都半成品。是否先集中把一个模块做到"能拿给人看"？
5. **投入产出的止损线在哪？** 用户已经明确表示"投入产出比不如别人 1 亿 token 的东西"，
   这是产品判断，不该由我继续用"再修一轮"来回答。
