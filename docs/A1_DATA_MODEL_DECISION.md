## 一、现状（实测）

| 表示 | 位置 | 几何 | 谁在用 |
|---|---|---|---|
| **高度图** `heightmap` | 行星：`mapData[planetId].heightmap`<br>剧本：`baseMaps[key].heightmap` | `grid.points` / `grid.spacing` / `cellsX` / `cellsY` | 行星笔刷、派生、智能放置；剧本渲染、笔刷、文化/宗教 |

**两份高度图互不相通**：`.map` 导入时 `scenarioEditing.importPlanetLayerData`（`:1026`）只拷 provinces/states/cultures/religions，**不拷 heightmap**。
**同向依赖是错的**：`usePlanetHeightBrush.buildFromTerrain()` 反过来用 `terrain[].elevation` 生成高度图初值 —— A1 之后这会变成「派生数据覆盖真源」。

## 二、三个选项

### (a) 两边共用一份对象（双向共享引用）
两边各自持有对同一对象的引用，谁改都同步。

- ✅ 真单源，不需要"同步"这个概念
- ❌ 必须建立 `baseMap ↔ planet` 的绑定，但**不是每张底图都有对应行星**（用户可以建纯剧本底图）
- ❌ 两侧 undo 快照会互相污染（剧本的 undo 快照里装着行星的高度图）
- ❌ 两侧的 `heightmap` 变体本就不同：剧本版多 `culture`/`religion` 逐格数组，行星版多逐格 `biome`；Azgaar 导入版**没有逐格 biome**。硬合并会把差异压进一个对象，渲染各自要读的字段变得不可预测

### (b) 以行星为准、剧本单向派生（**复制**一份给你）
行星是源，剧本底图从行星"拉取"一份高度图。

- ✅ 方向明确，实现简单
- ❌ **复制即双源**：拉过来之后就各活各的，漂移必然回归 —— 这正是当前问题的成因
- ❌ 在剧本侧涂的山，回不去行星（要么丢，要么再开一条"回写"通道，等于变成 (a) 的复杂度）

### (c) ★ 行星为单一真源，剧本底图按 `planetId` **代理**（推荐）
`baseMaps[key]` 记一个 `planetId`。**绑定了就走行星那份**（读与写都走，不复制）；**没绑定就保留自己的**（自建底图，行为不变）。

- ✅ 有绑定 = 真单源，天然一致，不需要同步逻辑
- ✅ 没绑定 = 向后兼容，旧项目与自建底图一行不改
- ✅ **不需要数据迁移** —— 因为不复制，就没有"把旧数据搬过去"这一步（A1 最大的风险点直接消失）
- ✅ 差异字段各留各的：剧本版多出来的 `culture`/`religion` 只是"绑定对象上的附加层"，不冲突
- ⚠️ 代价：所有高度图读写必须**改走一个访问器**，不能再直接摸 `baseMaps[key].heightmap`（这是一次机械但必须彻底的替换）

**为什么不选 (a)/(b)**：两者都试图让"两份数据保持同步"，而同步本身就是漂移的来源。(c) 的做法是**让它只有一份**。

> ### ⚠️ 实施中发现的重要修正：「只切读点」是错的
> 本文件最初把 M1 写成「所有读点先切到访问器（写路径暂不动）」。**动手时发现这条不成立**：
> 底图侧的写入模式是「**整体替换 baseMap 对象**」——
> `baseMaps.value = { ...baseMaps.value, [key]: { ...baseMap, heightmap: { ...hm, h } } }`。
> 这种写法**一写就把引用换掉**，天然与"共享引用"冲突。若只切读点，绑定后就会变成
> **「读行星那 (份) / 写自己那份」** —— 用户以为改了、画布不变，比不切更糟（静默分裂）。
>
> 所以实际拆成三小步：**M1（读取点 + 基础设施）→ M1b（写入点）→ M1c（开放绑定入口）**。
> 中间任何一步单独上线都**零行为变更**（未绑定时读与写都落在底图自己那份，与从前完全一致），
> 这是刻意的：把"一次大改"切成"三次可验证的小改"，每步都能跑全量回归。

## 五、风险（按严重度）

1. **静默数据丢失** —— 已有三处先例（P1/P2 已修，P3 未修）。原则：**任何"派生数据反过来写回真源"的路径都必须显式、可见、可撤销**。
2. **三套几何参数不对齐** —— `heightmap.grid`（cellsX/cellsY/spacing）与 `terrainGrid`（gridWidth/gridHeight/gridOriginX/gridOriginY/cellWorldSize）是**两套独立栅格**。M1 必须定下"谁是参考系"（建议：以 `heightmap.grid` 为唯一参考系，`terrainGrid` 降为它的一个派生视图）。
3. **序列化** —— 高度图/网格是 TypedArray，漏挂 `jsonSafeReplacer` 或漏建 `ensure*` 自愈 = "重启后高度图变空数组"，且**不报错**。
4. **可借助的现成范式** —— `provinceEditing.js` + `provinceShape.js` 已经实现「单一几何源 + 栅格派生 + 形状签名防漂移 + 投影回多边形」。M1/M2 应直接照搬这套（尤其 `shapeSignature` 自愈判据），不要从零发明。

## 六、边界情形：行星不存在（剧情上已毁灭 / 不打算建）怎么办？

**答案：不绑定 —— 让底图自己持有一份高度图。这是一等场景，不是兼容兜底。**

绑定只对「当前存在、且要在行星地图里编辑」的星球有意义。已毁灭 / 不打算在实体树里建节点的星球，走**底图自持**这条路：底图持有自己的高度图，全部笔刷与派生照常可用。

⚠️ **但这条路径此前是断的**（2026-09-24 补）：底图的高度图原先**只有 `.map` 导入一条来源** —— 新建的底图里高度 / 群系 / 文化 / 宗教笔刷与一键派生全都表现为「**点了没反应**」（`!hasGrid(hm)` 直接 return，几乎没有反馈）。已补 `createBaseMapHeightmap()`（按地形包围盒外扩生成网格，空底图给默认方框）+ 底图选择器旁的「创建高度图」按钮。

### 三种状态必须严格区分（`resolveHeightmap` 的返回值）

| 状态 | `owner` | `heightmap` | `dangling` | 含义 |
|---|---|---|---|---|
| **未绑定** | `self` | 底图那份 | false | 自建底图 / 已毁灭星球 → **正常路径** |
| 绑定了、行星**存在** | `planet` | 行星那份 | false | 真单源；行星还没高度图时返回 `null`（正常的"还没创建"） |
| 绑定了、行星**不存在** | `self` | **回落自身** | **true** | 悬空绑定 → 保住数据 + 提示用户解绑或重绑 |

第三行是关键：**「绑定即只认行星」不能无条件成立** —— 行星被删（剧情毁灭）时若还坚持返回 `null`，底图的高度图会**凭空消失**，用户只看到"地图怎么空了"。

### 与「毁灭」表达方式的关系 —— ✅ 已定并实现（2026-09-24）

用户决策：**毁灭只是叙事状态；实体可以保留，也可以根本不建。** 两条路都已支持：

| 做法 | 适用 | 实现 |
|---|---|---|
| **保留实体 + 状态标记** | 想在实体树里看得见它 / 想让它与行星共享同一份高度图 | `utils/entityStatus.js`：`active`（默认）/ `destroyed` / `ruined` / `sealed` / `lost` / `unknown`；详情面板可编辑（走 undo），项目面板显示徽标，**5 个画布上做视觉淡化** |
| **不建实体，只建底图** | 纯粹只要一张历史地图，不需要它出现在实体树里 | 不绑定 → 底图自持高度图（`createBaseMapHeightmap`） |

🔴 **状态的两条硬约束**（写进代码注释与单测）：
1. **状态只影响"怎么显示"，不影响"数据是否存在"** —— 无论什么状态，坐标 / 地图 / 剧本数据一律完整保留。**绝不能因为标了「已毁灭」就清掉数据**，那正是历史地图赖以存在的东西。
2. **未知值一律回落 `active`** —— 脏值不能让人误以为某颗星球已经毁灭；"存在"是最安全的默认假设。

### 在 Obsidian 里怎么写（✅ 已实现，2026-09-24）

词条 frontmatter 加一行即可，两种写法都认：

```yaml
---
层级: 行星
status: destroyed        # 推荐：英文 id（与 coordinate 同为机器字段）
---
```

```yaml
---
层级: 行星
状态: 已毁灭              # 中文别名也认（迁就中文库里手写）
---
```

认得的写法：6 个 id（`active` / `destroyed` / `ruined` / `sealed` / `lost` / `unknown`），
外加各自的**中文 label**（`已毁灭` / `已荒废` / `已封印` / `已失联` / `状态未知`）与
**短标签**（`毁灭` / `荒废` / `封印` / `失联` / `未知`）。
认不出 / 留空 / 写 `存在` → 一律落成 `null`（视作未设置），**不报错、也不写脏值**。

**方向：单向。** 笔记是权威来源，司天只读、不回写（与 `coordinate` 相反 —— 那个是司天写进笔记、提取时读回）。
在司天里改状态 → 存进**项目文件**；想改回笔记，就在 Obsidian 里改。

### 画布淡化（✅ 已实现，2026-09-24）

状态只在面板上显示是不够的 —— **画布上看不出来，这个功能就只完成了一半**（世界构建时是在图上找东西的）。

| 视图 | 绘制入口 | 覆盖对象 |
|---|---|---|
| GalaxyMap | `drawGalaxyNodes` | 恒星系（含低 LOD 的简化分支） |
| SystemView | `drawSystemStar` / `drawSystemPlanets` | 恒星 + 行星 / 卫星 |
| SystemDetailView | `drawStar` / `drawPlanets` | 恒星（含双星）/ 行星 / 卫星 |
| PlanetMap | `planetDrawing.drawPlaces` | 行星地图上的聚落 |
| AreaMap | `drawNodes` | 区域地图上的聚落 / 建筑 |

三条设计约定：

1. **`FADED_ALPHA = 0.45`** —— 取值区间是「看得出退后、但仍读得清标签」。太低（<0.3）用户会以为数据丢了，太高（>0.6）就与其他实体区分不开。
2. **`focused` 优先** —— 选中 / 悬停 / 匹配命中 / 拖拽中的实体**不淡化**。淡化的目的是「一眼看出一堆实体里哪些已经不在叙事里」；你一旦选中或悬停它，说明你正在关注/编辑它，此时弄模糊只会碍事。**编辑优先于装饰。**
3. **`save/restore` 必须成对** —— `globalAlpha` 是 canvas 全局状态。GalaxyMap 的 lod 分支有一个**中途 `return`**，save 之后必须先 restore。`test_entity_status` 用文本计数守住这条（save 数 = restore 数，GalaxyMap 是 1:2）。

**验证分三层**（各管一段，缺一段就会留下「看起来做了」的盲区）：

| 层 | 守什么 | 位置 |
|---|---|---|
| 纯函数单测 | `fadedAlpha` 语义（focused 优先、脏值不淡化、取值区间） | `test_entity_status` |
| 接线守卫（读源码） | 7 个绘制入口都调 `fadedAlpha`、save/restore 成对、5 个画布都接 `statusRevision` | `test_entity_status` |
| **像素级 CDP（test_66）** | **画布上真的变了，且只变那一点；改回来逐像素复原** | `test_66_entity_status_fade` |

`test_66` 的做法值得记：先 `focusOn` 把探针聚落放到画布中心并放大到 2x，采三帧 ——
`before`（active）→ 改 `destroyed` → `mid` → 改回 `active` → `after`，然后断言：
① `mid` 与 `before` 的差异**显著**（maxDelta ≥ 20）且**局部**（< 5% 像素）、包围盒落在画布中心附近；
② **`after` 与 `before` 逐像素完全一致（diff === 0）**。

② 是最强的那条：它一次性排除了「相机移动 / 整体重绘差异 / 别的节点被连带改动」等一切其他解释。
之所以能这么断言，是因为**选对了视图** —— PlanetMap 无动画循环（无 `startAnimation`、无 flicker），
背景与地貌都是确定性哈希；GalaxyMap 有 `animationTime` 驱动的闪烁，做不了复原断言。
⚠️ 反向验证过：把 `FADED_ALPHA` 临时改成 `1`（淡化失效），`test_66` 立即报 `diffPixels: 0`，
同时单测的区间守卫也变红（12/13）—— 证明这套断言真的在测淡化，而不是「插了代码没跑到」。

⚠️ **一个必须知道的坑：状态改了画布不会自动重绘。**

`store.updateNode` 是 `Object.assign(node, updates)` —— **就地改字段**，既不换 `nodes` 数组引用、也不换节点对象。于是所有「监听数组 / 对象引用」的浅 watch 全都捕捉不到 status 变化；而 GalaxyMap / SystemView / SystemDetailView 的绘制还用的是**布局副本**（`{...node, x, y}`），连 `store` 里改过了也读不到旧副本。

解法：store 提供单调递增的 `statusRevision`，`updateNode` 在 **undo 与 redo 两处**都递增（漏了就会「撤销后淡化不还原」）；各画布 watch 它 —— 持有副本的三个视图（GalaxyMap / SystemView / SystemDetailView）还要重建副本，不能只 `requestRender`。`test_entity_status` 守住这条接线。

> 实现细节：`status` **不进** `ENTITY_SHAPE_KEYS` 白名单，靠 `entityExtras()` 双向自动往返 —— 所以 `projectSchema` 一行都不用改。
> （反过来：若给它加显式字段，`nodeToProjectEntity` 的 `if (k in entity) continue` 会跳过它，画布上改的状态反而会丢。）

## 七、一句话

**A1 的正确形态不是"让两份数据同步"，而是"让它只有一份"。**

## 八、M1b 实施记录 + 绑定（M1c）的 5 条风险（2026-09-25）

> §七 是 M1 阶段（09-24）的结论。本节来自 M1b 落地**当天**的一次用户复核 ——
> 暮雨的原话：「历史剧本是三大模块中最独立完整的、一次施工永久存档，**强行将剧本与大世界地图中的行星数据绑定会不会有风险**？」
> **复核结论：质疑成立 —— 但风险不在「共用一份高度图」这个设计本身，而在三处尚未就绪的机制，以及一条价值冲突。**

### 8.1 M1b 做了什么（未绑定路径零行为变更）

5 个写入入口（`applyHeightBrush` / `applyBiomeBrush` / `applyCultureBrush` / `applyReligionBrush` / `deriveAllLayers`，各含 undo+redo 共 10 处）从「整体替换 `baseMap` 对象」改为 `commitHeightmap`。三处配套：

- **`commitHeightmap(key, hm, { touch })`**：`touch:false` 供 undo 用 —— 原来的 undo 闭包不写 `updatedAt`，不补这条会让「撤销」也改时间戳（与改动前不一致）。另：**悬空绑定回落到底图自身**，旧实现 `if (!planet) return;` 等于静默吞掉这次编辑。
- **R3 修复**：`changeNodeId` 的采集根补 `baseMaps` **值槽**。`baseMaps[*].planetId` 是「以节点 id 为值」的引用，不级联则行星改名（含转正）后绑定悬空；而绑定期底图侧那份已被 `delete` → `resolveHeightmap` 的 dangling 回落也拿不到东西 → **底图表现为空地图**（数据还在 `mapData` 里，只是没人指得到）。⚠️ 只采**值**：baseMaps 的**键**语义混用（既可能是行星名又可能是 id），刻意不列入 `idRefDicts`。
- **R5 修复**：派生 Worker 异步回写的落盘通道**按归属分流** —— 写入已经在 `mapData[pid]`，却仍排 `scheduleAutoSaveScenarios()` = 不落盘。

### 8.3 本质：不是「绑定有风险」，而是「绑定被用错了对象」

§二 否掉方案 (b)「复制」的理由是「复制即双源、漂移必然回归」。**这条对「正在与行星同步构建的当代地图」成立，对「历史存档剧本」不成立** —— 存档要的恰恰是「冻住」：行星后来怎么改都不该动它。

### 8.4 M1c 的设计修正

1. **双模式**：`导入并冻结`（复制一份进 `baseMaps`，**默认**，服务历史存档剧本，UI 明示「这是某时刻的副本，不再跟随行星」）+ `跟随行星`（= 现在的绑定，**显式选择**，服务当代地图）
2. **取消原计划的「`.map` 导入 / 行星→剧本导入时自动绑定」** —— 自动绑定会把冻存剧本悄悄接到活行星上
3. 绑定态加两条硬约束：**一星一图**（或至少显式确认）；剧本视图标注「地形来自行星 X，编辑它会改变行星地形」
4. **R1 的补充**：绑定态下剧本回滚必须显式说明「不含地形」，或提供「把当前行星地形冻结回底图」的解绑并复制动作

### 8.5 验证（`test_67`）

源码静态守卫（5 个入口的**函数体**内都必须出现 `commitHeightmap`、不得残留旧形态）+ 四态行为断言：未绑定（自持）/ 绑定（真单源）/ id 级联 / 悬空回落。

**反向探针 4 枚全部命中**；其中第一轮暴露了**一处假绿并已修**：`undo` 与 `redo` 落在**同一毫秒**时 `updatedAt` 相等 → 「undo 不打时间戳」这条断言恒真。修法是在两次操作之间跨毫秒（`await tick(25)`），修后探针立即报红（实测 `redo …797Z` vs `undo …823Z`）。

> 教训：**凡是「比较时间戳是否变化」的断言，都必须先保证两次操作跨毫秒** —— 否则它不是弱断言，而是**恒真断言**。

### 8.6 R1 的实测数据：快照机制**本来就不适合**装高度图（2026-09-25）

R1 起初被描述成「绑定后地形失去快照保护」。查代码与实测后，真实情况是**两面**：

| | 高度图位置 | 快照体积（满 50 份） | 能否回滚地形 |
|---|---|---|---|
| **未绑定（现状）** | `scenarios.baseMaps[k].heightmap` | ❌ **38.23 MB** | ✅ |
| **绑定后** | `maps[planetId].heightmap` | ✅ ~0 | ❌ |

实测方式：`esbuild` 把 `projectSchema.js` 单独打包成 CJS，构造 26910 格（= 真实 fixture 规模）的高度图，**模拟连续涂 50 笔**、每笔后 `pushSnapshot`（`projectStore.saveProject` 每次落盘都会 push），量 `JSON.stringify(snapshots)` 的体积：

- 单份高度图 JSON = **1263.4 KB**
- 现状（含高度图）：第 1 份 1.23 MB → 第 10 份 8.03 MB → **第 50 份 38.23 MB**
- 高度图不进快照：**0.01 MB**

**根因**：`diffWalk` 明确选择「**数组/原始值整体替换**」（注释：路径式 diff 不索引数组，否则插入一项会产出几十条位移改动）→ 高度图的 `h`/`temp`/`prec`/`biome` 四个数组**任何一个变了，整份数组都要进 patch**。而 `SNAPSHOT_DIFF_KEYS` 里含 `scenarios`，注释却写着「KB 级」—— 这个假设在底图有了高度图之后就不成立了。

⚠️ **暮雨当前的真实项目（`绒花计划.sitian`）仍是 KB 级** —— 机制已就位、尚未触发（他的剧本侧还没涂过地形）。

**三个方案（2026-09-25 决策 → 已选 A）**：

| 方案 | 做法 | 体积 | 代价 |
|---|---|---|---|
| **A ✅ 已实施** | 高度图（及 `terrainGrid` / `referenceImages` 等同级重字段）**从快照里排除**；回滚时这些字段**保留当前值**（不是删掉），UI 明示「回滚不含地形」 | 38 MB → **4.7 KB** | 快照不再回滚地形；地形保护降级为「最近 10 份整文件备份」（`projectHandler` 的 `.backups/`，**已存在**，含完整高度图） |
| **B（未采纳）** | 保持现状 | 38 MB | 用户一涂地形项目文件就膨胀；绑定后地形又失去回滚 |
| **C（未采纳）** | 高度图单独走**专档轮转备份**（`<项目>.sitian.terrain/`，保留 N 份） | ~6 MB（N=5） | 多一条恢复通道 + 一套 UI；实现量与风险最高 |

> A 与绑定后的行为**一致**（快照不含地形）—— 好处是两种状态语义统一，不会出现「绑定了地形就突然不能回滚」这种状态相关的意外。

### 8.7 方案 A 的落地（2026-09-25）

`utils/projectSchema.js`：
- 新增 `SNAPSHOT_HEAVY_FIELDS = ['heightmap', 'terrainGrid', 'referenceImages']`
- `snapshotState()` 走 `stripHeavyFromValue()` 剔除它们（**快照写盘方向**）
- `restoreSnapshot()` 走 `carryHeavyIntoValue()` 把**当前项目**的重字段补回重放结果（**回滚方向**）
- 新增 `snapshotStateWithHeavy()` —— 专供回滚的 `before`（undo 闭包必须能原样还原，否则「回滚 + 撤销」会吃掉地形）

`store/projectStore.js`：`restoreProjectSnapshot` 的 `before` 改用 `snapshotStateWithHeavy`。
`components/ProjectPanel.vue`：快照区写明「**不含地形高度图与参考图**」+ 回滚提示补一句。

**实测（复跑同一脚本）**：snapshots 第 50 份 **38.23 MB → 4.7 KB**；回滚到第 1 份后**当前高度图仍在**；`before` 含高度图 ✓。

**守卫**：`test_46` 新增 6 条断言（高度图不进快照、轻字段与省份多边形仍在、回滚保留高度图、`snapshotStateWithHeavy` 含重字段、`snapshotState` 不含）。

> ⚠️ **探针教训（值得跨项目复用）**：这两半（**剔除** 与 **补回**）会**互相掩盖** ——
> 同时装两枚探针时，「回滚保留高度图」照样通过（因为剔除去掉后快照里又有高度图了），
> 看起来像"探针没生效"。**必须一次一枚单独验证**：单独装「补回」那枚才报出

### 为什么 `test_68` 的两组断言必须**互为反面**

同一句「在剧本里涂山」：冻结模式下行星**必须不变**，跟随模式下**必须变**。
只测一边等于没测 —— 「两边其实是同一份」与「其实从来没接上」这两种**完全相反**的 bug，都能骗过单边断言。

⚠️ 反向探针还暴露了一个反直觉的点：把 `cloneHeightmapForFreeze` 退化成 `return hm`（共享引用）后，
**「在剧本涂山不影响行星」这条行为断言仍然通过** —— 因为 `commitHeightmap` 是**整体替换**而不是原地改字段，
所以即便共享了引用，涂山也不会改到行星那一份。真正抓到它的是**对象身份断言**
（`bm.heightmap !== pHm`、`bm.heightmap.h !== pHm.h`）。

> **教训：判断"两份数据是不是同一份"必须用身份断言（`!==` / `===`），不能只用行为断言。**
> 只要写入模式是"替换"而非"原地改"，行为断言对共享引用就是**盲的**。

## 十、M2（= A2）第一步：高度图栅格渲染跨视图共享（2026-09-25）

**问题**（§一 实测的渲染侧成因）：同一份高度图，两个视图各有一套管法 ——
ScenarioMap 逐格上色 → 离屏 canvas；PlanetMap `buildLabelOutlines` → 矢量平滑轮廓。
结果：**同一颗行星在剧本里和在行星地图里是两个世界**，而且改一处配色另一处不会变（又一处双源）。

**做法**：新增 `utils/heightmapRaster.js`，把「高度图 + 配色方案 → 离屏 canvas」抽成纯函数层
（色带常量 / `cellColor` / `fillPixelBlock` / `buildHeightmapRaster(hm, kind)` / `createRasterCache()`）：

- `ScenarioMap` 改为引用它（颜色与阈值**逐字**搬过去 → **零行为变更**），只保留「用哪份高度图」与缓存失效时机
- `PlanetMap` 新增 `drawHeightmapRaster(ctx, kind)`；缓存失效用**内容指纹**（复用轮廓缓存的 `hashLabels(hm.h)`）
  —— 涂抹时 h 变 → 指纹变 → 自动重建，**不需要任何外部 clear**。
  （对比：ScenarioMap 的栅格缓存只在切底图 / 卸载时清，**涂抹期间是陈旧的** —— 既存行为，本次未动。）
- UI：PlanetMap 高度笔刷参数区加「着色」下拉（`data-testid="heightmap-raster-kind"`，只在高度模式渲染），
  五档：`biome`（默认 = 原矢量群系着色）/ `landsea` / `height` / `temp` / `prec`

**默认仍走 biome → 零行为变更**：矢量那套是为解决「逐格绘制 + 画布滤镜卡死」重写的
（见 `planetDrawing` 352 行那段踩坑记录），群系着色信息量也更大；栅格是**补上**「与剧本视图对齐」的那一档，
不是替代。

### 实测（`test_69`）

切到 `landsea`：画布绝大多数像素变化（栅格确实铺开）；**切回 `biome`：逐像素复原（`diff === 0`）**。
源码守卫：两个视图都引用共享模块，且组件里**不得残留**色带常量 / `cellColor` / `fillPixelBlock`
—— 「又复制一份」是这类重构最常见的回退方式，而且它**不会报错**，只会让两个视图慢慢再次分叉。

### 三个踩坑（都值得复用）

1. **漏了 watch 接线**：切换档位没有 `watch(heightmapRasterKind) → requestRender()` →
   「下拉改了、画布没反应」。像素断言直接抓到（`diffPixels: 0`）。
   > **静态守卫与纯函数测试都看不见这一类缺陷** —— 「接线是否真的通到画面上」只能靠像素断言。
2. **探针互相掩盖（第二种形态：段间 fail-fast）**：一次装两枚探针**只报出第一枚** ——
   用例 Python 侧在 f1 失败后 `return`，f2 根本没跑，看上去像"第二枚探针没生效"。
   修法：多段用例改为**累积失败**而非 fail-fast（每段都要有机会说话）。
   > 与 §8.7 那条是同一类教训的两个面：**探针之间不能有「谁先失败谁闭嘴」的结构**。
3. **栅格边缘透明像素 / 两档数据**：断言「landsea 只有两色」要跳过 `alpha === 0` 的像素
   （包围盒外扩后边角没被方块覆盖，RGB 读出来是 0,0,0 → 会多出一色，实测踩到）；
   断言「height 是多色」时数据必须给**连续梯度** —— 只给 8 / 60 两档，线性插值色带只会命中两个采样点。

## 十一、M2（= A2）第二步：`terrain[]` 降为可选覆盖物（2026-09-25）

**问题**：PlanetMap 的地形主表示是多边形（不透明实色、画在最前），高度图只是默认关闭、画在**所有元素之上**的叠加层
—— 那个位置正是「只能默认关着，否则像遮罩」的成因，也正是 A2 所说「手绘几何编辑器观感」的根因。

**真正的难点不在渲染，而在「同一件事要在三个地方回答」**：画布渲染 / 命中检测 / 导出（PNG·SVG）。
三处各写一套 `if`，就是又一个「改一处另两处不变」的双源 —— 而且**不会报错**。

**做法**：新增 `utils/terrainRepresentation.js`（纯函数）作为**唯一判定**，三处共用：

| 输入 | 有高度图 | 无高度图（自建底图 / 旧多边形地图） |
|---|---|---|
| 地形主表示 | **高度图**（不透明 `1.0`；与多边形同显时 `0.75`） | **多边形**（不透明 `1.0`，**与从前逐像素一致**） |
| 多边形 | 默认**不画**；`terrainPolygons` 图层打开时半透明 `0.5` 叠加；编辑多边形时自动亮起 | 主表示（就是它） |
| 命中 | 仅当多边形**确实画着**（`terrainHit`）——「看得见才点得到」 | 同左 |

- `layers.planet` 新增 `terrainPolygons`、**删除 `heightmap`**（职责被「地形」总开关吸收；它原本没有 UI 入口）。
  「地形」按钮从此是**总开关**，内容由数据决定 —— 因为图层开关是**全局单例**，而「有没有高度图」是**每颗行星各自的**，
  不可能靠改某个开关的默认值来实现数据驱动。
- 高度图渲染位置从「所有元素之上」**移回地形槽位**；涂色网格（`terrainGrid`）的显示条件从「死绑 `terrain` 图层」
  改为**地形有显示即可**（否则关掉总开关改看覆盖物时，涂色层会凭空消失 —— 这是本步改出来的一个真 bug，被 `test_59` 抓到）。

### 同批修掉的两条真缺陷

1. **导出链此前完全没有高度图**：`useFullMapExport` 的 PNG/SVG 里只有 `drawTerrain` → 高度图驱动的行星导出后地形是**空的**。
   现在导出与画布读同一份判定；SVG 里高度图以**内联位图**承载（栅格数据在矢量格式里只能如此，与参考底图同手法）。
2. **导出按「屏幕视口」剔除**：`drawHeightmap` 的视口剔除是屏幕优化，导出时会把屏幕外的地形整块丢掉
   —— 不报错，只是导出的图悄悄缺一大片。故导出必须 `{ full: true }`。
