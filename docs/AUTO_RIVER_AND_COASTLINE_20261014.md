# 自动河流与海岸线裁剪（2026-10-14）

> 状态：**已落地**（0.3.1 待打包）。对应暮雨 2026-10-14 实测反馈第 2、5、7 条，
> 以及第二轮实测的三条：**折线僵硬 / 随机出海 / Shift 框选没反应**。
> 其余反馈（3/4/6/8/9/10）的结论见文末「没做的 / 判断」。

---

## 一、结论先行（TL;DR）

1. 「自动河流」一次点击同时踩了**两个独立缺陷**，叠在一起表现为「毫无征兆卡死 → 一片空白 → 点什么都没反应」：
   - **崩溃**：`ScenarioMap.renderFrame` 画自动河流那一段写的是裸 `ctx.save()`，而 `ctx` 是
     `ref(null)`。`<script setup>` 里**只有模板**会自动解包 ref → 函数体里 `ctx` 是 `{value}` 对象
     → `ctx.save is not a function`（压缩后就是用户看到的 `Ce.save is not a function`）。
     它抛在 `renderFrame()` 里 ⇒ **从那一行起后面全不画**（省界/标签/小地图/势力名一起没了），
     连续 3 帧后渲染护栏自我暂停。
   - **同步分钟级循环**：旧 `generateRivers` 对每个高地格**全表扫描**找最低邻居。
     真实底图实测量级：`desite` 9975 格 / 399 源头；行星 26910 格 / 281 源头，
     单点全表扫描 **7.46 ms** → 内层迭代 ≈ 1500 亿次 ≈ **分钟级**，而它是同步跑的
     —— 主线程从点下按钮那一刻就不再响应任何事件（Windows 随后把窗口标成"未响应"）。
2. 修完之后**同一个按钮**在 5625 格的实景下 **~160 ms**；崩溃归零。
3. 第二轮实测又抓出**三件**（都是真缺陷，逐条有实测数字）：
   - **同一段里的第二个崩溃**：渲染块按「点数组的数组」访问河流（`river[0].x`），而追踪器
     返回 `{points, flow}` 对象 → `river.length` 是 undefined（跳过判断失效）→ 首帧抛
     `Cannot read properties of undefined (reading 'x')`。**只修 `ctx` 仍然是一片空白。**
   - **「僵硬折线」**：格心连成的折线（实测**转角中位数 41.6°、最大 113°**）+ 所有河一样粗
     （汇流量算错，恒为 1 —— 见 §2.3）。
   - **「Shift 框选没反应」**：手势**本身是通的**（用真实鼠标输入验过，见 §4），
     不通的是**回音**：条件不满足时它静默变成平移。
4. 「河流依旧随机出海」——两条都修了，但**其中一半不是 bug，是这份数据的地形**（见 §2.5）。

## 二、为什么会这样（逐条对码）

### 2.1 `ctx` 不解包 —— 一个"默认永不执行"的分支里的运行时炸弹

```js
const ctx = ref(null);                       // :1379
...
if (autoRivers.value.length > 0 && showRivers.value) {
  ctx.save();                                // ← 旧代码：ctx 是 ref，save 是 undefined
```

- `npm run build` 不报错（属性访问在运行时才炸）；
- `test_undefined_identifiers.js` 抓不到（`ctx` **声明得好好的**，不是未声明标识符）；
- 102 个 CDP 用例抓不到 —— `autoRivers` 默认是空数组，**这一整块默认永远不执行**。

**这是本项目第五次出现"某个入口零调用所以从没被跑到"的缺口**（前四次：`clearOwnership` /
`batchSetOwnership` / `removeProvinceWithGrid` / `updateScenario`）。

### 2.2 第二个 bug：同一段里的数据形态假设

`river.length` / `river[0].x` 假设"每条河是点数组"，而追踪器返回对象。两个 bug 在**同一行附近**，
只修一个仍然一片空白 —— `test_103` 因此把「渲染没暂停 + `renderErrorCount === 0` +
画布上真有河色像素」三条一起断言。

### 2.3 汇流量算错（"所有河一样粗"的根因）

线的粗细分级靠 `flow`（汇流量 = 累积上游格数）。第一版有两个错，**每个都让 flow 恒为 1**：

| 错误 | 后果 | 实测 |
|---|---|---|
| 累加顺序写成**升序** | donor 交量时 receiver 早已处理完 → 量全丢 | `maxFlow` 只有 2 |
| `flow` 取**路径起点** | 河源没有上游，起点 flow 恒为 1 | 每条河 flow 都 = 1 |

判据已钉进单测：**「flow 必须真的累积」**（斜面 12 列上最大汇流必须 ≥ 12，实测 55）。

### 2.4 排水网的三次返工（值得留档：同一个目标，三种假象）

要让河流"像河"，必须同时满足：**单调下降**（不走上坡）、**能到海**、**在谷地汇聚**。
三种实现各错一半：

| 实现 | 单调性 | 能到海 | 汇聚 | 实测假象 |
|---|---|---|---|---|
| 插入式优先队列从海向上洪泛（priority-flood） | ❌ **237 格流向比自己更高的格**（另 71 格等高） | ✅（按构造） | ❌ 平均链长 1.47 | 一片**放射状**短支沟 + "水往高处流" |
| 陡坡下降（只认严格更低的邻居） | ✅（按构造） | ❌ 3055 陆格里 **1499 个是洼地** | ✅ | 一半陆地没有出口，河网碎成短沟 |
| **填洼（priority-flood 抬水位）+ 陡坡下降 + 升序累加** | ✅ | ✅ | ✅ | —— |

**当前的键**：`水位` 主键（保证出得去）+ `原始高度` 副键（同样水位时沿真实谷地走）+ 下标兜底
（严格全序 → 不成环）。两个键的先后顺序也都踩过一次：
- 只按原始高度 → 洼地全是终点，真实底图**最长河道 10 格 / 144 世界单位**（岛宽 1700）；
- 只按水位 → 每格朝**离海最近**方向走，同样是放射状短沟。

**填的是流向场，不是数据**：`filled` 只在本函数内存里活着，**绝不写回高度图**。

### 2.5 「随机出海」：一半是 bug，一半是这份地形

- **bug 那一半**：高程是**格心采样**，海岸线从格子里穿过 → 一批"明明泡在水里"的格子高度 ≥ 20。
  它们够高时就被当源头，河道从海边起步、朝最陡方向射进大洋。
  现在注入**陆地判定**（省份多边形掩膜，`utils/coastline.js` 的同一份实现），
  源头必须**离海 ≥ 2 格**（真实底图实测挡掉 11 个）。
- **地形那一半（据实交代）**：这份底图的高度图与"画出来的陆地"形状差得很远。
  实测对照（9975 格）：

  | 判据 | 陆地格数 |
  |---|---|
  | 省份多边形掩膜（画布上真正画出来的那块） | 2960（29.7%） |
  | 高度图 `h ≥ 20` | 3055（30.6%） |
  | 两者一致 | 2954（**只差 107** —— 两份口径其实很一致） |

  而这座"岛"的**最远陆点离海只有 11 格（158 世界单位）**，岛本身却横跨 1913 单位 ——
  也就是说它是**一片细碎群岛 + 狭窄半岛**，陆地格平均离海不到 2 格。
  在这种地形上，水**本来就走不了多远**：实测排水链直方图
  `0-2 步: 2401 格 / 3-5 步: 538 / 6-10 步: 21`。
  → **自动河流在这份数据上不可能生成长江大河**，这是数据分辨率（133×75）与地形形状决定的，
  不是渲染或算法问题。要长河，得先把高度图换成分辨率更高、能形成连续坡面的一份。

### 2.6 河网形态（相对汇流量闸门）

| `channelInit` | 出图 | 点数中位 | 汇流中位 | 总画线长度 |
|---|---|---|---|---|
| 1（**现用默认**） | 111 条 | 5 | 12 | **6912 单位**（≈ 3.6 × 岛宽） |
| 2 | 10 条 | 5 | 20 | 648 单位 |
| 6 | **0 条** | — | — | — |

⚠️ **别把 `channelInit` 当"只留大江"用**：这份地形的汇流量量程极窄（中位 12 / 最大 21），
调大一点点就会把整张图清空。主次靠**线宽**（`Math.cbrt(flow)`）体现，不靠砍条数。

### 四条算法口径（改 `riverTrace.js` 前必读）

1. **水只往低处流**：接收者严格更低。旧实现取"半径内最小者"不判高低 → 能走上坡。
2. **不能到海的洼地不成河**：靠"填洼 + 只有能到海的格才算河源"两件事合起来保证。
3. **邻居口径不变**：半径仍是 `spacing × 1.5`（不换 8 邻域 —— 换了"升级前后流出来的河不一样"，
   而这种变化看起来只是"河流位置变了"，没人会想到是口径改了）。
4. **填洼只填流向场**，绝不写回高度图（与 A1「高度图写入统一走 `commitHeightmap`」同源）。

## 四、「Shift 框选没反应」——查清了：手势是通的，回音不通

第二轮实测里我**没有**凭感觉改代码，而是先补了一条**只认真实鼠标输入**的用例
（`test_104`：CDP `Input.dispatchMouseEvent`，走浏览器真实命中测试与事件顺序）：

```
相机 {'x': 314, 'y': 90, 'scale': 1.13}；拖 (469,726) → (1011,183)
拖动中 marquee=有；松手后选中 4 个
提示：「框选到 4 个顶点（都不与邻省共边，拖动只改这一个省）；Esc 取消选择」
不按 Shift 拖同一段 → 平移照旧（相机真的动了）
```

**结论：手势在真实输入下工作正常**（顺带说明：这条用例第一版我连写三次坐标都错了 ——
相机被适屏覆盖、端点落到画布外、省份没经 store 建 —— 每次都表现为"手势不通"。
这也说明**以前的测试为什么漏了它**：`test_102` 用的是 `new MouseEvent(...)` **合成事件**，
它比真实浏览器宽松 —— 本项目在右键菜单上已经吃过一次同样的亏，见 AGENTS 的 test_88 条）。

那用户为什么觉得"没什么作用"？最可能是**前置条件不可见**：
框选有两条静默前提 —— ① 工具必须是「改形状」（顶点编辑）；② **必须先选中一个省份**，
而且只框得到**那个省**的顶点。条件不满足时旧代码**直接静默变成平移**（"Shift 没用"）。

修法（纯反馈，零行为变更）：
- 顶点模式下 **Shift+拖永远起得来框**（不再依赖"已选省"）；
- 没选省时状态栏直接告诉他：先用「选择 (V)」点一下要精修的省；
- 框里没顶点时，文案改成「这一框里没有**「某省」**的顶点 —— 框选只作用于当前选中的省」
  （旧文案是「要框住紫色圆点」，在"根本没画紫色圆点"时等于没说）。

## 六、如实交代（没做的 / 判断）

1. **自动河流的结果不落盘**（内存预览）：切走视图或换底图就没了。本轮只把这件事写进 title
   与按钮态。要落盘得先定「自动河是什么身份」（`river_*` 前缀会被手画河的 CRUD 当成用户资产）。
2. **这份底图上的河就是短的**（§2.5 有实测）：地形是细碎群岛，"长河"在这一层数据上出不来。
   要长河请先换更高分辨率的高度图（或提高「刷新底图数据」时的高度图格数）。
3. **内陆湖还没有一等公民**：数据模型里湖是 `landFeatures` 的多边形（不参与省份/归属），
   画布上按海色渲染；`kind: 'sea'` 的省份要**手画**再把属性面板切到「海域」。
4. **道路/聚落同样与省份轮廓错位**（实测 496 条路里 36.8% 顶点在陆外，最长一段 184 点；
   617 个城镇里 44 个在陆外）。本轮**没裁它们** —— 路是稀疏折线，按陆地裁会把长段整条删掉。
5. **地形"模模糊糊"的量级已量清、没改渲染**：desite 高度图 133×75 = 9975 格 / spacing 14.4，
   在 1900×1080 世界单位上 ⇒ 栅格输出 531×294 px，被放大到 ~1920 宽 = **每格约 3.6 屏幕像素**。
   升级路径（双线性超采样 / 等值带）早已评估在
   [`TERRAIN_RENDER_SMOOTHING_PLAN.md`](TERRAIN_RENDER_SMOOTHING_PLAN.md)，本轮没动。
6. **`heightMath.smoothHeightmap` / `heightMath.generateRivers`** 是同款旧实现且**零调用**，
   本轮没删（`smoothHeightmap` 也是 O(n²)：26910² ≈ 7.2×10⁸ 次）。
